# 결정 기록 · 제품·범위·작업 방식

[결정 기록 색인](../decisions.md)의 한 주제다. 번호·앵커(`#d-xx`)는 색인 전체에서 고유하다. 아래 "현재 규칙 요약"은 이 주제의 유효한 규칙을 줄인 것이고, 정본은 그 아래 조항이다. 조항 안의 "개정 2026-10-25"는 그날 바뀐 문구이며 이전 문장은 조항의 원문 연결 또는 [개정 전 판](https://github.com/fvoci/GroundZero/blob/8349771265af71e70d628bd48abe94f815d8f29c/docs/decisions.md)에서 본다.

## 현재 규칙 요약

- fvoci는 새로 만든 앱이며 PostgreSQL·Rust·Svelte·Tiptap·CRDT·Meilisearch·rhwp를 쓴다(D-01~D-04).
- 다섯 모듈 유형(프로젝트·연구·스터디·강의·취미)을 같은 유형으로도 여러 개 만들 수 있고, 내부 ID는 UUIDv7, 사람용 번호는 모듈 인스턴스 안에서 원자적으로 증가한다(D-15~D-17, D-48).
- 셀프호스트와 SaaS는 같은 조직 테넌트 모델을 쓴다(D-07, D-111).
- 같은 정보는 한 정본으로 여러 화면에서 재사용하고, 표시·저장·권한을 구분하며, 사용자에게 Markdown·내부 ID 이해를 요구하지 않는다(D-12).
- @ 링크 키는 모듈 안에서 고유하고, 옛 키는 같은 모듈만 되돌릴 수 있다(D-18).
- 기능 범위·권한·삭제/보존·비용·외부 서비스는 사용자 결정, 그 안의 구현 선택은 검토자가 정하고 이유를 남긴다(D-43, D-47). 검증은 명령·SHA·결과로 기록한다(D-42).
- v1.0.0 원격 태그 전에는 하위호환을 보장하지 않고 호환 전용 코드를 두지 않는다(D-92).
- 오버홀 수락 기준은 프로젝트 업무·일정 조정 대표 경로, 입력 보존 시험 전부, 백업 복구 1회 실측이다(D-128).

## 조항

<a id="d-01"></a>

- **D-01 신규 개발, 이름 fvoci.** 빈 저장소에서 새로 시작한다. 초안 §2의 기존 FVOCI 확장 여부를 대체한다. 근거: 사용자.

<a id="d-02"></a>

- **D-02 PostgreSQL만 지원.** 초안 §2의 DB 지원 범위 미정을 대체한다. 최소 버전과 환경별 범위는 D-100. 근거: 사용자.

<a id="d-03"></a>

- **D-03 기본 기술 구성.** Rust 백엔드, Rust xtask 개발·빌드·검증, Svelte 프론트엔드, pnpm, Tiptap 블록 편집, CRDT 공동 편집. 근거: 초안 §2·사용자.

<a id="d-04"></a>

- **D-04 검색과 HWP 뷰어.** Meilisearch와 rhwp를 쓴다. rhwp의 형식별 실제 호환성은 별도 검증 대상이다(O-11). 근거: 초안 §2·사용자.

<a id="d-05"></a>

- **D-05 미리보기 범위.** PDF·이미지·텍스트·Office·HWP/HWPX 읽기 미리보기를 포함하고, Office·HWP 본문 편집·수정본 저장은 제외한다(X-01). Office 엔진은 비교 평가 후 선택한다(D-54·D-71·D-74, O-10). 근거: 초안 §17·사용자.

<a id="d-07"></a>

- **D-07 셀프호스트 우선, SaaS 고려, 공개 시점.** 셀프호스트를 먼저 완성하고 SaaS를 고려한다. 합의한 전체 기능을 갖춘 뒤 제품을 공개하되, 내부 구현·검증은 작은 사용자 흐름부터 단계적으로 한다. 개발 저장소·CI 이미지의 선공개는 D-65. 개정(2026-10-25): 셀프호스트와 SaaS 모두 조직 › 워크스페이스 테넌트 모델(D-111)을 쓴다. 근거: 초안 §1·사용자.

<a id="d-11"></a>

- **D-11 제품 목적.** 프로젝트·연구·스터디·강의·취미의 업무·문서·일정·자료·시간을 한곳에서 관리하고 연결한다. 중복 입력을 줄이며 한눈에 보고 빠르게 찾게 한다. 개인·소규모 팀 모두 지원하고 혼자 쓸 때 불필요한 협업 절차를 강제하지 않는다. Plane·Kaneo·Outline의 유용한 경험을 참고한다. 근거: 초안 §1.

<a id="d-12"></a>

- **D-12 구현 원칙.** 같은 정보·상태는 한 정본으로 여러 화면에서 재사용하고 모듈마다 공통 기능을 재구현하지 않는다. UI 표시와 저장 성공, 읽기와 수정·복제·다운로드 권한을 구분한다. 실패·재시도·동시 편집·권한 철회·복구도 검증한다. 사용자에게 Markdown·내부 ID 이해를 요구하지 않는다. 공개 범위는 합의 목록이며 추가 아이디어는 후속이다(X-08). 근거: 초안 §20.

<a id="d-14"></a>

- **D-14 용어.** 위키는 공간 공용 지식, 문서는 위키·모듈 콘텐츠, 모듈은 다섯 기능 유형, 항목은 개별 프로젝트·연구·스터디·강좌·취미 활동이다. 목록은 항목 탐색, 보기는 목록·칸반·달력 등의 표현, 워크플로는 업무 상태·전환이다. 모듈 안은 ‘프로젝트 위키’ 대신 ‘프로젝트 문서’ 등으로 부른다. 근거: 초안 §3·사용자.

<a id="d-15"></a>

- **D-15 다섯 유형과 모듈 복수 생성.** 프로젝트·연구·스터디·강의·취미를 제공하고 같은 유형도 DEV·OPS처럼 여러 모듈을 만들 수 있다. 초안 §21의 미정을 대체한다. 근거: 사용자.

<a id="d-16"></a>

- **D-16 모듈 이름.** 표시 이름은 사용자가 정하고 이름을 바꿔도 내부 기능 유형은 유지한다. 근거: 초안 §4.

<a id="d-17"></a>

- **D-17 ID·배지·번호.** 워크스페이스 내부 ID는 UUIDv7이며 표시 이름 중복을 허용한다. 같은 이름은 색상 배지·아이콘·보조 정보로 구분하고 색상은 자동 지정 또는 사용자 선택이다. 권한·참조는 내부 ID를 쓰며 각 항목의 내부 ID는 불변이다. 사람용 번호는 공간·모듈 인스턴스 범위에서 원자적으로 증가한다(D-48). 삭제 번호 재사용·정렬/이름 변경에 따른 재매김·재시도 중복 생성을 금지하고 빈 번호는 허용한다. 근거: 초안 §4·사용자.

<a id="d-18"></a>

- **D-18 @ 링크와 사용자 언급.** 위키 참조 키는 WIKI, 모듈은 이름과 짧은 키를 분리한다(`@A/DEV-1`, `@영환`). 사람·항목·문서·업무를 구분해 찾고 선택 대상은 내부 ID, 표시는 배지·번호·제목을 쓴다. 같은 공간에서 대소문자를 무시해 키 중복을 막고 WIKI를 예약한다. 이름·키 변경 뒤 연결을 유지하며 옛 키는 별칭으로 남긴다. 다른 모듈은 그 키를 재사용할 수 없고, 같은 모듈이 옛 키로 되돌리는 것은 허용한다(개정 2026-10-25). 동명 후보는 사용자가 고른다. 언급은 담당 지정·권한 부여가 아니며 링크·역방향 링크·멘션 알림에 원본 접근권한을 적용한다. 항목과 그 안의 문서는 별도 대상이다(D-48). 근거: 초안 §5·사용자.

<a id="d-26"></a>

- **D-26 보호 범위의 한계 안내.** 복제·다운로드 제한이 화면 촬영까지 막는다고 설명하지 않는다. 근거: 초안 §7.

<a id="d-42"></a>

- **D-42 품질 검사 검증 기록 방식.** 검사 설정을 구현하고 대표 위반을 실제로 잡는지 확인한다. 명령·대상 SHA·결과·필요한 실패 로그를 PR이나 작업 보고에 남기며 별도 증거 프레임워크는 만들지 않는다. O-24 해소. 근거: 사용자.

<a id="d-43"></a>

- **D-43 열린 항목의 처리 방식.** 사용자 결정과 기술 설계를 구분한다. 기술 설계는 검토자가 근거·권장안·대안을 제시하고 구현 시 진행한다. 기능 축소·권한 확대·새 서비스·비용은 사용자 결정으로 남긴다. 근거: 사용자.

<a id="d-44"></a>

- **D-44 보류 항목의 취급.** 운영자 대상 암호화(H-01)·외부 자동 시청 추적(H-02)은 필수 범위의 차단 항목이 아니다. 새 승인 없이 범위를 확대하지 않는다. 근거: 사용자.

<a id="d-47"></a>

- **D-47 사용자 결정과 구현 선택의 경계.** 기능 범위·권한·삭제/보존·비용·외부 서비스는 사용자 결정이다. 파일명·배치·lint·검증 기록 방식은 승인된 원칙 안에서 검토자가 정하고 이유를 간단히 남긴다. 모든 구현 선택을 승인 대기로 만들지 않는다(D-43 구체화). 근거: 사용자.

<a id="d-92"></a>

- **D-92 최초 정식 릴리스 전의 하위호환 정책.** 과거 개발 버전의 하위호환을 보장하지 않고 그 호환만을 위한 불필요한 코드를 유지하지 않는다. 근거: 사용자(2026-10-21).
  - 경계는 정식 `v1.0.0` 태그의 **원격 push**다. 로컬 태그 생성·배포 완료가 아니며 원격 게시 뒤 상세 호환 정책은 별도 결정한다. D-87의 태그 불변성·별도 승인 규칙은 유지하며 SaaS 자동 배포를 뜻하지 않는다.
  - 확정된 새 설계가 대체한 API·설정·SQL·자료구조의 호환 분기/별칭/fallback은 제거한다. 대체 근거와 현재 호출자·흐름·기존 데이터 영향을 먼저 확인하고 코드·시험·문서·seed를 함께 갱신하며 명령/SHA/결과를 남긴다(D-42).
  - 지원 PostgreSQL·Supabase 간 호환, 다중환경 어댑터, 정상 복구·재시도는 유지한다. fallback이라는 이름이나 복수 경로만으로 제거하거나 환경·권한·정합성 요구를 줄이지 않는다.
  - DB 초기화·데이터 임의 삭제의 승인이 아니다. 영향·복구 방안을 제시해 별도 승인받는다(D-88 포함).
  - D-89의 옛 호출 호환, D-91의 옛 요청/클라이언트/schedule-preview 유지만 대체한다. 현재 필요한 무조건 이동·기본 관계 생성, 동시성·재배치 승인·정합성은 유지한다.
  - 선택적 코드 전반 감사에 잔존 호환 코드와 제거 근거·영향을 포함하되 구현·병합·릴리스의 새 필수 관문으로 만들지 않는다.

<a id="d-128"></a>

- **D-128 오버홀 수락 기준.** 대표 경로는 프로젝트 업무·일정 조정이다: 항목에서 업무 만들기 → 담당·기한·선행 지정 → 칸반·간트에서 조정 → 다음날 다른 세션에서 내 업무·홈에서 찾아 이어서 하기. 이 경로를 실제 브라우저 회귀 시험의 첫 시나리오로 두고 밝음·어두움, 1280px·375px에서 돌린다. 복구 증명은 두 가지다: (1) 저장 응답 유실·판 충돌·권한 철회·계정 전환 뒤 입력 보존과 재시도 시험 전부를 새 권한 모델에서 통과한다. (2) 연구·프로젝트 예시 데이터(문서 1천 건·첨부 1 GB 규모)로 백업 → 빈 설치 복구를 한 번 실측해 소요 시간·누락 여부를 기록한다. RPO·RTO 수치 목표는 이 실측 뒤 사용자가 정한다. O-38·O-40 해소. 근거: 사용자(2026-10-25).
  - 개정 2026-10-26: 계정 전환 취소·실패의 헤드리스 Chromium 자동시험 통과는 (1)의 일부다. 수동 조작, 화면 있는 브라우저, Safari·실기기, 실제 탭 전환 감지, 문서 편집과 계정 전환의 결합은 4단계 수락 표의 별도 항목이며 실기기·Safari는 사용자가 확인한다. 근거: 사용자(2026-10-26 A-1).
  - 개정 2026-10-27: 웹 단계 리뷰 게이트: 변경 파일이 CodeRabbit 검토 한도(300개)를 넘어 실제 검토가 불가능하면, 최종 HEAD의 변경 파일 전부를 독립 검토자(Codex 한도 중에는 Claude)에게 분할 배정해 근거표·모든 지적 처분·필수 CI 전부 SUCCESS를 확인한 결과로 그 단계의 CodeRabbit 실행 요건을 대체한다. CodeRabbit은 PASS로 표시하지 않고 NOT RUN(한도 초과)으로 기록한다. PR·base·필터·권한·비용은 바꾸지 않는다. 근거: 사용자(2026-10-27 R5 B).
