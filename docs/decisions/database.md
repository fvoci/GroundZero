# 결정 기록 · SQL·DB·마이그레이션·보존

[결정 기록 색인](../decisions.md)의 한 주제다. 번호·앵커(`#d-xx`)는 색인 전체에서 고유하다. 아래 "현재 규칙 요약"은 이 주제의 유효한 규칙을 줄인 것이고, 정본은 그 아래 조항이다. 조항 안의 "개정 2026-10-25"는 그날 바뀐 문구이며 이전 문장은 조항의 원문 연결 또는 [개정 전 판](https://github.com/fvoci/GroundZero/blob/8349771265af71e70d628bd48abe94f815d8f29c/docs/decisions.md)에서 본다.

## 현재 규칙 요약

- PostgreSQL 최소 17, 검증한 17·18, 표준·셀프호스트 Supabase·Supabase Cloud가 같은 제품 SQL·RLS를 쓴다(D-100).
- 새 행 UUIDv7은 앱이 공급하고 DB 기본값·생성 함수는 두지 않는다. 앱 역할은 `fvoci_app` NOBYPASSRLS, 마이그레이션은 `fvoci_migrator`다(D-88).
- 제품 SQL 정본은 `crates/server/migrations/` 하나이며 최종 정의 기준으로 통합한다. 정식 `v1.0.0` 전의 오버홀 SQL도 같은 규칙으로 다시 통합하고 개발·시험 DB는 재생성하되 삭제는 별도 승인이다. 그 뒤에는 새 마이그레이션을 더한다(D-107, D-126, D-131).
- 달리는 아비시니안 오버홀 순서는 SQL → 서버 → 웹 → 도구이고 단계마다 Draft PR이다(D-126). 다음 오버홀도 이 틀을 기본으로 한다(D-131).
- 휴지통 기본 30일, 참조 중인 자료 버전·묶음은 자동 삭제하지 않고 되살릴 수 있다(D-41, D-56, D-69).

## 조항

<a id="d-41"></a>

- **D-41 휴지통 보존 기간.** 기본 30일이며 관리자가 설정할 수 있다. 최초 기록에서 누락됐던 선택 9번을 보완했다. 근거: 선택 9번·사용자.

<a id="d-56"></a>

- **D-56 자료 버전 보존.** 분석 기록·보존 중인 문서 리비전이 참조하는 버전은 자동 영구 삭제하지 않는다. 미참조 버전은 권한자가 정리하고 보존 기간·저장 한도를 설정한다. 용량 초과 시 참조 버전을 몰래 지우지 않고 알린다. O-15 해소, P-09 확장 채택. 근거: 사용자.

<a id="d-69"></a>

- **D-69 참조로 보존된 만료 휴지통 묶음의 되살리기.** 살아 있는 기록·문서의 버전 참조 때문에 자동 삭제를 미룬 묶음은 만료 뒤에도 되살릴 수 있다. 관리자·지운 사람이라는 기존 권한을 유지하고 참조 버전 자동 삭제 금지(D-56)도 유지한다. O-35 해소. 근거: 사용자(2026-10-17).

<a id="d-88"></a>

- **D-88 셀프호스트 Supabase를 DB 배포 대상으로.** 기존 자체 PostgreSQL 지원·기본 설정과 Rust 서버·Keycloak/OIDC·S3/R2/local·Meilisearch·작업 대기열을 유지한다. Supabase Auth/Storage/Realtime/Data API·화면의 직접 DB 접근을 추가하지 않는다. 당시 Cloud 제외는 D-100의 공통 구현 설계·검증 대상으로 대체됐다(원격 변경 승인 아님). 근거: 사용자(2026-10-20).
  - 관리자는 superuser일 필요가 없다. bootstrap은 **변경 전에** 기존 두 역할의 SUPERUSER/CREATEROLE/BYPASSRLS, 앱 역할의 CREATEDB도 금지하고 관리자 ADMIN OPTION(간접 포함)을 확인한다. 문제 시 무변경 종료, 정상일 때 속성은 유지하고 비밀번호만 갱신한다. 역할·멤버십·스키마 변경은 한 트랜잭션이다.
  - 관리자는 두 역할을 만들었거나 ADMIN OPTION이 있어야 한다. 소유자로 할 작업은 상속 없는 SET 멤버십을 잠시 받아 원복한다. 기존 멤버십은 삭제하지 않고 옵션만 되돌리며 복구 연결이 끊기면 새 관리자 연결로 한 번 더 원복한다. 복구 관리자 권한은 session_replication_role 설정에만 쓴다. 그 능력은 superuser, Supabase supautils 허용 또는 일반 PostgreSQL에서 superuser의 GRANT SET ON PARAMETER로 준비한다.
  - 새 행 UUIDv7은 Rust Uuid::now_v7()이 만든다. DB id 기본값·UUID 생성 함수/트리거는 두지 않는다. 생성 함수는 마지막 p_ids에서 차례로 소비하고 부족 FV001은 HTTP 409/작업 트랜잭션 전체 재시도, 잘못된 ID FV002는 500이며 대체 생성하지 않는다. 가변 행 수는 같은 트랜잭션의 <함수>_ids가 상한(권한 없으면 0)을 주고 표는 uuid_extract_version(id)=7을 검사한다. PG17에 uuidv7()를 따로 만들지 않는다.
  - 문서 제목 감사는 제목을 바꾸는 두 경로가 app_audit_document_rename으로 남기고 리비전의 전후 제목을 읽어 리비전당 한 번 기록한다. 개발 SQL도 xtask가 넘기는 ID를 쓴다. 상세 호출·재시도는 [제거 전 UUID 계약](https://github.com/fvoci/GroundZero/blob/8349771265af71e70d628bd48abe94f815d8f29c/docs/sql-id-contract.md)(D-127).
  - 사용자 지시로 기존 마이그레이션의 id 기본값을 고쳤다. 당시 개발 DB는 checksum 불일치로 재생성이 필요하지만 삭제는 사용자 확인 뒤다.
  - 소유자는 fvoci_migrator, 앱은 fvoci_app NOBYPASSRLS, RLS는 트랜잭션 app.user_id를 쓰고 조직 경계를 포함한다(D-111). auth.uid()로 바꾸거나 fvoci 스키마를 Data API에 노출하거나 anon/authenticated에 권한을 주지 않는다.
  - Supabase CI job은 D-64 이미지 계약의 예외다. xtask가 호스트 Docker로 공식 구성을 띄우고 실패 후 정리 전에 상태/로그를 읽기 위해 호스트 러너에서 실행한다. 툴체인은 같은 고정 판이다. 이후 추가한 browser job의 예외는 D-64의 구현 선택을 따르며 다른 공통 이미지 job 계약은 유지한다.

<a id="d-100"></a>

- **D-100 PostgreSQL 최소 17과 검증한 메이저의 공통 구현.** 지원 목록에는 실제 검증한 메이저만 적고 ‘17 이상’으로 미래 메이저를 보장하지 않는다. 검증한 표준 PostgreSQL은 17·18이며 [환경별 결과](../self-hosting.md#postgres-support)를 구분한다. 근거: 사용자(2026-10-22).
  - 표준 PostgreSQL·셀프호스트 Supabase·Supabase Cloud는 같은 제품 SQL·마이그레이션·RLS·권한을 쓴다. 차이는 초기 DB/역할 준비 권한과 연결/TLS/pooler 설정뿐이며 설치자에게 내부 RLS·함수 수정을 요구하지 않는다.
  - D-88의 Cloud 제외를 공통 구현의 설계·검증 대상으로 대체한다. Rust/OIDC/기존 저장소/검색은 유지하고 Supabase Auth/Storage/Realtime/Data API에 의존하지 않는다. 공식 권한 안내·로컬 제한권한 실행·실제 Cloud 실행을 구분한다.
  - 최소 미달은 bootstrap/migrate에서 변경 전에 설정 오류로 거절한다. 기존 읽기 전용 Cloud 경로로 버전을 확인할 수 있지만 원격 변경/업그레이드/역할·비밀번호 변경/제품 설치를 승인한 것은 아니다.
  - 백업·복구도 공통이며 session_replication_role은 초기 권한 조건이다. 제한 계정의 거부를 Cloud 복구 불가·기능 제외로 해석하지 않는다. 관리형 스키마·기본 역할·객체·데이터를 보존하며 데이터 삭제/이전은 별도 승인이다.
  - PG17 미만은 지원하지 않는다. 운영 DB 자동 업그레이드·PG18 데이터 볼륨에 PG17 이미지 연결을 금지한다. Supabase PG15→17은 [공식 절차](https://supabase.com/docs/guides/self-hosting/postgres-upgrade-17)를 따르되 실행은 별도 결정한다.

<a id="d-107"></a>

- **D-107 최종 정의를 기준으로 SQL을 통합하고 개발·시험 DB를 재생성.** 누적 이력을 이어 붙이지 않고 최종 객체·의존 순서로 초기 마이그레이션을 구성한다. 제품 SQL 정본은 `crates/server/migrations/` 하나이며 비교용 과거 SQL은 고정 SHA로 참조한다. 새 기준의 주석도 현행 결정·계약에 맞춰 정리한다. 달리는 아비시니안 오버홀 SQL은 이 규칙으로 기준 SQL을 다시 통합한다(D-126). 근거: 사용자(2026-10-23).
  - PostgreSQL 최소 17, 검증한 17·18, 환경 공통 SQL, 앱 공급 UUIDv7, 기존 RLS·권한·경합·멱등성·재시도 계약을 유지한다. 2026-10-23 통합은 새 기능·정책 변경을 포함하지 않았다. 달리는 아비시니안 오버홀 통합(D-126)은 같은 통합 규칙을 쓰되 D-111~D-125의 승인된 변경을 반영한다.
  - 로컬 개발·시험 DB와 Supabase Cloud 테스트 DB는 새 SQL 기준으로 재생성한다. 기존 개발 DB의 자동 이전 호환 경로를 만들거나 SQLx 이력·체크섬을 덮어써서 업그레이드로 처리하지 않는다. 기존 DB로 시작하면 재생성이 필요함을 알리고 중단한다.
  - 재생성 방향 확정은 삭제 승인이 아니다. 실제 연결·소유·공유 관계, 정확한 대상과 데이터 소실 영향, 백업 존재·위치·확인 방법·복구 한계를 먼저 제시하고 최종 승인 후 해당 GroundZero 객체·데이터·이력만 정리한다. 백업 생략은 임의 결정하지 않는다.
  - Supabase 프로젝트·관리 스키마·기본 역할·다른 앱 객체, 로컬 Keycloak·첨부·다른 checkout 자원은 자동 포함하지 않는다. 검색 색인 정리가 필요하면 별도 대상·영향에 포함한다. 불명확한 공유 자원은 파괴적 단계만 멈추고 확인한다.
  - 구현·격리 DB 검증·별도 Draft PR까지 진행한다. main 병합·태그·배포는 포함하지 않는다. 실제 Cloud 초기화 후 앱 역할 CRUD·접근 거부·공간 격리를 확인하며 구버전 백업 복구는 실행한 범위만 보고한다.
  - 개정 2026-10-27: 오버홀의 SQL 기준 재통합은 정식 `v1.0.0` 원격 태그(D-92) 전까지만 한다. 그 뒤의 오버홀은 기존 설치가 올라올 수 있게 새 마이그레이션을 더한다(D-131). 근거: 사용자(2026-10-27).

<a id="d-126"></a>

- **D-126 오버홀 순서.** (1) SQL: 조직·역할 표, `app_access`, RLS 조직 경계, 상태 정의, activity, 알림 카운트·커서, 내 업무 집계, 시간 전환. D-107 규칙으로 기준 SQL을 다시 통합한다(추가 마이그레이션을 쌓지 않고 `202610250001`도 합친다). 개발·시험·Cloud 테스트 DB는 재생성하며 삭제는 D-107대로 별도 승인이다. (2) 서버: 권한 모듈 한 곳, 조직·서버 관리자 API, 새 집계 API. (3) 웹: 하위 경로 라우터, 전환기, 홈·내 업무·알림함, 모듈·항목 묶음, 업무 안 시간, 브랜드 토큰. (4) 도구·CI: 시험 도구의 실행 소유 자원 복구와 중복 실행 직렬화, 시험 스택 연결 수 여유(#130·#125·#93·#90), 개인용 단일 Compose 프로필(D-129). 수락 시험 기준은 D-128이다. 각 단계는 Storybook·브라우저 회귀 시험을 함께 바꾼다(D-108). 단계마다 Draft PR이며 main 병합·태그·배포는 별도다. 열린 이슈 중 제품·도구 경로에 걸린 것은 해당 단계가 흡수해 닫는다: 1단계 #85·#86·#87·#95·#101·#102·#115(예외 제거 시도), 2단계 #79·#83, 3단계 #50·#70·#76·#84·#88·#104·#108, 4단계 위 넷. #113(실제 Supabase Cloud CI 상시 운영)은 자격 증명·비용이 걸려 오버홀 밖이다. 근거: 사용자(2026-10-25).
