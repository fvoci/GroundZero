# Rust→SQL UUID 인자 계약

D-88과 [개발 지침 85.1절](development.md#851-id는-앱이-만든다)의 호출부 유지보수 지침이다.
UUIDv7 생성은 Rust 앱의 책임이다. SQL에 ID 생성을 맡기거나 설치자에게 추가 설정을 요구하지 않는다.
자체 PostgreSQL과 셀프호스트 Supabase DB에서 같은 계약을 사용하며 Keycloak/OIDC 구성과는 별개다.

## 어떤 ID를 넘기는가

| 인자                                     | Rust 호출부의 책임                                                                                                   |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 기존 대상 ID (`ItemId`, `DocumentId` 등) | 요청·조회에서 받은 값을 그대로 바인딩한다. 새로 만들지 않는다.                                                       |
| `request_id`                             | 기존 요청의 중복 처리 식별자를 유지한다. 새 행의 ID 목록으로 대체하지 않는다.                                        |
| 마지막 인자 `p_ids uuid[]`               | `db::new_ids(n)` 또는 `db::needed_ids(...)`가 만든 새 행 ID 목록을 순서대로 넘긴다.                                  |
| 개별 새 ID 인자                          | `app_audit_document_rename`의 첫 인자처럼 개별 UUID를 받는 호출은 기존 `Uuid::now_v7()` 생성·바인딩 위치를 유지한다. |

모든 UUID 인자가 `p_ids`인 것은 아니다. SQL 함수의 서명과 기존 호출의 인자 순서를 유지한다.
`new_ids`는 `Uuid::now_v7()`으로 생성한다. SQL은 받은 ID를 소비하며 부족분을 생성하지 않는다.
상한보다 실제 생성 행이 적으면 남은 ID는 버린다.

## 개수와 호출 순서

- 고정된 상한은 `.bind(new_ids(n))`로 충분하다. 예를 들어 `app_create_event`는 일정·감사 기록용으로 2개를 받는다.
- 입력 길이로 정해지면 기존 계산을 유지한다. 회차·스터디 단위 추가는 입력 개수 + 1, 업무 체크리스트 추가는 입력 개수, 업무 만들기(`app_create_task`, 0098)는 업무·만들기 감사 2개 + 담당자 수(겹친 사람 몫은 쓰지 않는다)다.
- DB 상태에 따라 달라지면 같은 트랜잭션에서 `<함수>_ids`를 본 호출 직전에 실행한다.
  `needed_ids`에는 **개수 산정에 필요한 인자를 바인딩한 쿼리**를 넘긴다. 본 함수의 모든 인자를 그대로 받는다는 뜻은 아니다.
  예를 들어 `app_update_task_ids`는 업무 ID·담당자 목록·일정 이동 목록만 받는다.
- `needed_ids`는 상한을 조회한 뒤 Rust에서 UUIDv7 목록을 만든다. 그 목록은 본 호출의 마지막 인자에 바인딩한다.
  조회와 본 호출 사이에 새 트랜잭션을 열거나, 재시도 바깥에서 ID 목록을 미리 만들어 재사용하지 않는다.
- 현재 `needed_ids`는 NULL·음수 상한을 빈 목록으로 처리한다. 빈 목록이어도 본 호출을 생략하지 않는다.
  대상 없음 등의 기존 오류 판단은 본 함수에 남긴다.

## 오류와 재시도

| 단계·오류                              | 유지할 처리                                                                                                          |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 상한 조회 실패                         | `needed_ids`가 기존 `AppError::from_db_function`으로 전달한다.                                                       |
| 본 호출의 `FV001` (ID 부족), HTTP 경로 | `AppError::from_db_function`의 409 응답. 실패한 트랜잭션을 커밋하지 않는다.                                          |
| 본 호출의 `FV001`, 작업 프로세스       | 원래 DB 오류를 유지한다. `worker::system_call`이 트랜잭션 전체를 상한 조회부터 다시 시도한다(첫 시도 포함 최대 3번). |
| `FV002` (잘못된 ID)                    | 기존 500 오류를 유지한다. 다른 ID를 만들어 조용히 대체하지 않는다.                                                   |

상한 조회와 실제 변경 사이에 대상 수가 늘 수 있으므로 상한은 예약이 아니다.
HTTP 호출과 작업 프로세스의 본 호출은 오류 전달 방식이 다르므로, 호출부를 공통화할 때도 각 경로의 오류 매핑과
재시도 책임을 유지한다. 실패한 트랜잭션에서 본 함수만 다시 부르지 않는다.
이 문서는 기존 계약을 설명하며 SQL 서명·마이그레이션·RLS·제약조건을 변경하지 않는다.
