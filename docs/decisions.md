# fvoci 결정 기록

작성일: 2026-10-17
상태: 기획 단계. 제품 코드 구현 전. 저장소 초기화 전.

## 이 문서의 사용법

항목은 다섯 범주로 나눈다. 범주를 섞지 않는다.

| 접두어 | 범주        | 뜻                                                                                    |
| ------ | ----------- | ------------------------------------------------------------------------------------- |
| D      | 확정 결정   | 사용자가 명시적으로 확정한 사항. 근거로 사용자 발언 또는 기획 초안의 절 번호를 남긴다 |
| P      | 미승인 제안 | 검토자가 제안했으나 사용자가 승인하지 않은 사항. 결정이 아니다                        |
| O      | 열린 항목   | 실제로 결정이 필요한데 아직 정하지 않은 사항                                          |
| X      | 범위 제외   | 이번 범위에서 빼기로 한 사항                                                          |
| C      | 확인 필요   | 원문을 확인할 수 없어 해석을 보류한 사항                                              |

표기 규칙

- 근거는 세 종류로 구분한다.
  - `초안 §n`: 2026-10-17 전달받은 "통합 작업·지식·학습 관리 앱 — 전체 기획 초안"의 절 번호. 전달받은 지침이다.
  - `지침`: 초안 외에 문서 형태로 전달받은 지침. 품질 기준 문구, Docker Compose 추가 전달 문구, 32개 선택 목록.
  - `사용자`: 대화에서 사용자가 직접 한 발언. 인용은 짧게 남긴다.
- 열린 항목은 두 종류로 나눈다. **사용자 결정**은 공개·공유·삭제·보존·권한·사용 경험·비용에 영향을 주는 정책이다. **기술 설계**는 확정된 정책을 구현하는 저장 구조·라이브러리·검사 설정·실행 구조이며, 검토자가 근거·권장안·대안을 제시하고 구현 시 진행한다. 단, 기능 축소·권한 확대·새 서비스나 비용 추가가 생기면 사용자 결정으로 올린다.
- `[대체]`: 이전 결정이나 초안의 미정 항목을 새 결정이 대체했다는 표시. 이전 내용을 함께 남긴다.
- `[기각]`: 검토자 제안을 사용자가 거부했다는 표시.
- `[해소]`: 열린 항목이 결정으로 닫혔다는 표시. 닫은 결정 번호를 남긴다.
- 검토자의 추천은 사용자 결정으로 바꾸지 않는다. 확정한 사항을 다시 미정으로 돌리지 않는다.
- 근거 없는 일정 추정은 기록하지 않는다.

## 0. 이해 요약

검토자가 정리하고 사용자가 "전반적으로 맞습니다"로 확인한 내용이다. 예시는 이해 확인용이며, 아직 정하지 않은 데이터 구조를 확정 사실로 쓰지 않는다.

fvoci는 빈 저장소에서 새로 만드는 통합 작업·지식·학습 관리 앱이다. 한 번 입력한 정보를 여러 화면에서 다시 쓰는 것이 핵심 원칙이고, 셀프호스트를 먼저 완성하되 SaaS를 함께 고려한다. Rust 백엔드, Svelte 프론트엔드, Tiptap 기반 블록 편집, CRDT 공동 편집, Meilisearch 검색, PostgreSQL 단일 DB가 기본 방향이다.

### 예시 1. 워크스페이스 → 모듈 인스턴스 → 항목·문서·업무

워크스페이스 A 안에 프로젝트 유형 모듈을 두 개 만들 수 있다. 하나는 이름 "개발", 키 DEV이고 다른 하나는 이름 "운영", 키 OPS다. 둘 다 유형은 프로젝트이며 내부 기능은 같다. DEV 모듈 안에는 개별 프로젝트 항목이 있고, 그 항목 안에 업무·문서·체크리스트·시간 기록이 붙는다. `@A/DEV-1`은 DEV 모듈 범위의 1번을 가리키며, 모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유하므로 DEV-1이 항목이면 DEV-2는 업무일 수 있다. 화면에서는 유형 아이콘과 제목으로 구분한다(D-48). 공용 위키는 모듈이 아니라 워크스페이스 직속이며 키 WIKI로 참조한다. 번호는 모듈 인스턴스마다 따로 증가하므로 DEV-1과 OPS-1은 다른 대상이다.

### 예시 2. 개인 노트와 관리자 열람

워크스페이스 A의 관리자는 A 안의 모든 문서를 열람할 수 있고, 멤버가 문서별로 비공개 설정한 문서도 포함된다(D-40). 반면 사용자 영환이 쓰는 개인 노트는 A의 관리자에게도 보이지 않는다. 그래서 개인 노트는 워크스페이스 소속 문서와는 다른 소유 구조여야 하는데, 개인 노트는 사용자 소유로 별도 관리하며 기본 비공개이고, 소유자가 특정 사람에게 읽기·수정 권한을 줄 수 있다. 공유해도 개인 소유는 유지되고 상대방의 워크스페이스 관리자에게 권한이 따라가지 않는다(D-49, D-59). 이 비공개는 앱의 권한 수준이며, 서버나 DB 운영자가 내용을 읽을 수 없게 하는 암호화는 확정한 요구가 아니다(H-01, 보류).

### 예시 3. 체크리스트의 여러 입력 방식

어떤 업무의 상세 화면에 에디터가 없더라도 체크박스와 내용 입력란이 있어 항목을 추가·완료할 수 있다. 문서 편집 화면에서는 본문 안에 체크리스트 블록을 쓸 수도 있고, 별도 체크리스트 입력 영역을 쓸 수도 있다. 사용자가 `- [x] 자료 수집`과 `- [ ] 초안 작성`을 붙여넣으면 두 항목이 완료·미완료 상태로 입력 영역에 채워지고 사용자가 확인·수정한다. 한 화면에 같은 체크리스트가 본문과 입력 영역 양쪽에 보이면 어느 쪽에서 바꿔도 결과가 같아야 한다. 체크 항목이 자동으로 업무가 되거나 강의를 완료시키지는 않는다. "업무로 전환"과 "기존 업무·강의 회차 연결"은 아직 제안 단계다(P-10). 체크리스트를 어디에 저장하고 어떻게 연결하는지는 설계 대상이다(O-04).

### 예시 4. 연구 파일 버전 관리

연구 항목에 `survey.csv`를 올리면 v1이 된다. 정제 후 같은 자료에 새 파일을 올리면 v2가 추가되고 v1은 남는다. 각 버전에는 업로더·시각·변경 설명이 기록된다. 분석 기록 "회귀분석 1차"는 데이터 v1과 코드·결과 파일의 특정 버전을 연결한다. 이후 v3이 올라와도 "회귀분석 1차"는 v1을 가리킨다. 이전 버전은 열람·다운로드할 수 있다. 앱은 코드를 실행하지 않고, 업로드한 파일 내부의 차이 분석이나 실험 자동 추적도 하지 않는다. 앱에서 작성한 문서의 리비전·diff·복원은 별개이며 확정 범위다(D-27).

## 1. 확정 결정

### 1.1 제품·기술

- **D-01 신규 개발, 이름 fvoci.** 빈 저장소에서 새로 시작한다. 근거: 사용자 "빈 저장소에서 신규 개발, 이름은 fvoci". `[대체]` 초안 §2 "기존 FVOCI의 확장인지 별도 앱인지 ... 별도로 확정한다".
- **D-02 PostgreSQL만 지원.** 근거: 사용자 "PostgreSQL만 지원". `[대체]` 초안 §2 "최종 DB 지원 범위는 별도로 확정한다".
- **D-03 기본 기술 구성.** 백엔드 Rust, 개발·빌드·검증 명령 Rust xtask, 프론트엔드 Svelte, 패키지 관리 pnpm, 편집기 Tiptap(노션형 블록 편집), 공동 편집 CRDT. 근거: 초안 §2, 사용자 "Rust + xtask + Svelte + pnpm + Tiptap + CRDT가 기본 방향".
- **D-04 검색과 HWP 뷰어.** 검색은 Meilisearch. HWP/HWPX 뷰어는 rhwp 기준. rhwp의 형식별 실제 호환성은 검증 대상이다(O-11). 근거: 초안 §2, 사용자.
- **D-05 미리보기 범위.** PDF·이미지·텍스트·Office·HWP/HWPX 읽기 미리보기를 포함한다. Office·HWP 본문 편집과 수정본 저장은 제외한다(X-01). Office 미리보기 엔진은 비교 평가 후 선택한다(D-54, O-10). 근거: 초안 §17, 사용자.
- **D-06 파일 저장과 업로드.** S3 호환 또는 서버 로컬 스토리지. 청크 업로드·재개·재시도·무결성 확인. 완료 요청 중복 처리 방지. 취소·만료 업로드의 잔여 데이터 정리. 파일 다운로드 권한 확인. Cloudflare 경유 시 개별 요청 크기 제한 안에서 전송하고, 완료 단계에서 파일 전체를 거대한 요청으로 다시 전송하지 않는다. 최대 파일 크기·총 저장량은 운영 설정으로 관리한다(D-52). 근거: 초안 §2, §17.
- **D-07 셀프호스트 우선, SaaS 고려, 공개 시점.** 셀프호스트를 먼저 완성하고 SaaS 운영을 함께 고려한다. 합의한 전체 기능을 갖춘 뒤 공개한다. 내부 구현·검증은 작은 사용자 흐름부터 단계적으로 한다. 전체 기능 공개 목표가 한 번에 모든 코드를 작성해야 한다는 뜻은 아니다. 근거: 초안 §1, 사용자 "합의된 전체 기능을 갖춘 뒤 공개하되 내부 구현·검증은 단계적으로".
- **D-08 SaaS·격리·운영 원칙.** 데이터의 소유 워크스페이스를 명확히 기록한다. 워크스페이스 간 공유는 명시적인 권한으로 처리한다. 관리자 열람은 자기 워크스페이스 범위에 한정한다. 개인 시간 기록의 비공개 정책을 별도로 유지한다. PostgreSQL RLS와 앱 권한 검사를 함께 설계한다(세부 정책 O-09). 앱 실행 역할과 운영·마이그레이션 역할을 분리한다. 검색·첨부·캐시·실시간 연결·백그라운드 작업에도 격리를 적용한다. 셀프호스트와 SaaS에서 핵심 데이터와 권한의 의미를 일치시킨다. 근거: 초안 §19.
- **D-09 Rust·TypeScript 품질 기준.** rustfmt·Clippy 필수, 고정 툴체인에서 CI 경고를 오류로 처리, 제품 코드의 무분별한 unwrap·expect·panic 금지, 오류 버림 금지, 자체 코드 unsafe 기본 금지, 의미 있는 타입, async 책임 명시, Clippy 규칙 선택적 활성화. TypeScript strict와 명시 옵션, svelte-check, 타입 정보 기반 ESLint, unknown에서 시작하는 외부 데이터 검증, any·이중 단언·@ts-ignore 금지, 비동기 오류·취소·오래된 응답 처리, 수명주기 해제. Rust↔TypeScript 계약 단일화와 런타임 검증, 전송 표현 결정, 상태 정본 명시. 검사·예외 규칙과 복잡도 원칙. 전문은 `docs/development.md`. 현재는 문서화 단계이며 코드 초기화 단계에서 실제 설정과 검증 명령으로 강제한다. 근거: 지침(품질 기준 문구) "fvoci의 Rust·TypeScript 품질 기준을 결정 기록과 개발 지침에 추가한다".
- **D-10 Docker Compose 개발·통합 테스트 환경.** PostgreSQL·Meilisearch·테스트용 S3 호환 저장소를 컨테이너로 실행한다. D-45에 따라 격리된 Keycloak도 테스트 컨테이너에 포함한다. 운영 서비스나 개인 개발 DB를 테스트에 쓰지 않는다. 이미지·Compose·의존성 버전을 저장소에서 관리하고 로컬과 CI가 같은 이미지와 검사 명령을 쓴다. 빌드 이미지와 실행 이미지 분리, 병렬 실행 격리, UID/GID 검증, 시크릿 분리, privileged·Docker 소켓·호스트 전체 마운트 금지, 동시 실행 수 제한, 자기 자원만 정리, 호스트 도구 허용 범위, xtask·pnpm 진입점. 전문은 `docs/development.md`. 현재는 문서화 단계이며 저장소 초기화 단계에서 실제 설정을 구현한다. 근거: 지침(추가 전달 문구) "개발·통합 테스트 환경은 Docker Compose를 기준으로 구성한다".

### 1.2 제품 목적과 구현 원칙

- **D-11 제품 목적.** 프로젝트·연구·스터디·강의·취미에서 발생하는 업무·문서·일정·자료·시간 기록을 한곳에서 관리한다. 여러 서비스에 같은 내용을 반복 입력하는 불편을 줄인다. 입력한 정보를 한눈에 보고 빠르게 찾는다. 문서·업무·자료·사람을 연결한다. 개인 사용자와 소규모 팀을 모두 지원한다. 혼자 사용할 때 불필요한 협업 절차를 강제하지 않는다. Plane·Kaneo·Outline의 유용한 경험을 참고한다. 근거: 초안 §1.
- **D-12 구현 원칙.** 동일한 정보는 한 번 입력하고 여러 화면에서 재사용한다. 같은 상태를 문서·폼·업무 DB에 독립적으로 중복 관리하지 않는다. UI의 체크 표시와 실제 저장 성공을 구분한다. 읽기 권한과 수정·복제·다운로드 권한을 구분한다. 실패·재시도·동시 편집·권한 철회·복구 상황도 검증한다. 공통 기능을 모듈마다 별도로 재구현하지 않는다. 사용자에게 Markdown이나 내부 ID 이해를 요구하지 않는다. 공개 범위는 이번 합의 목록으로 고정하고 추가 아이디어는 후속 목록으로 관리한다(X-08). 근거: 초안 §20.

### 1.3 구조·명칭

- **D-13 워크스페이스.** 사람·권한·콘텐츠를 묶는 공간. 한 사용자는 여러 워크스페이스에 속할 수 있다. 워크스페이스 안에는 홈, 위키, 프로젝트·연구·스터디·강의·취미 모듈, 검색·내 업무·최근 항목·즐겨찾기·알림을 둔다. 근거: 초안 §3.
- **D-14 용어.** 위키 = 워크스페이스 공용 지식 공간. 문서 = 위키 또는 모듈 안에서 작성하는 콘텐츠. 모듈 = 프로젝트·연구·스터디·강의·취미라는 기능 유형. 항목 = 개별 프로젝트·연구·스터디·강좌·취미 활동. 목록 = 항목을 모아 탐색하는 화면. 보기 = 목록·칸반·달력·간트 등 표현 방식. 워크플로 = 업무 상태와 전환 과정. 모듈 내부는 '프로젝트 위키'가 아니라 '프로젝트 문서', '연구 문서'로 부른다. 근거: 초안 §3, 사용자.
- **D-15 다섯 유형과 모듈 복수 생성.** 프로젝트·연구·스터디·강의·취미의 다섯 유형을 제공한다. 같은 유형의 모듈도 DEV·OPS처럼 여러 개 만들 수 있다. 근거: 사용자 "같은 유형의 모듈을 DEV·OPS처럼 여러 개 생성 가능". `[대체]` 초안 §21 "같은 유형의 모듈을 여러 개 만들 수 있는지, 이름만 바꾸는지".
- **D-16 모듈 이름.** 모듈의 표시 이름은 사용자가 정한다. 내부 기능 유형은 이름 변경과 무관하게 유지한다. 근거: 초안 §4.
- **D-17 ID·배지·번호.** 워크스페이스 내부 ID는 UUIDv7. 워크스페이스 표시 이름 중복 허용. 이름이 같은 공간은 색상 배지·아이콘·보조 정보로 구분하고, 배지 색상은 자동 지정 또는 사용자 선택. 권한 검사와 참조는 내부 ID로 처리. 각 항목에 변하지 않는 내부 고유 ID. 사람이 보는 번호는 워크스페이스·모듈 범위에서 원자적으로 증가. 삭제된 번호 재사용 금지. 번호 사이 빈 번호 허용. 정렬·이름 변경으로 재매김하지 않음. 요청 재시도로 중복 생성 금지. 동일 유형 모듈이 여러 개이므로 번호 범위는 모듈 인스턴스를 구분해 설계한다. 번호가 세는 대상은 D-48. 근거: 초안 §4, 사용자 "번호 범위는 모듈 인스턴스를 구분해 설계해야 합니다".
- **D-18 @ 링크와 사용자 언급.** 공용 위키의 참조 키는 WIKI. 모듈은 사용자 지정 이름과 짧은 참조 키를 분리한다. 예: `@A/DEV-1`, `@A/LAB-1`, `@A/CLASS-1`, `@A/WIKI-1`, 사용자 언급 `@영환`. @ 입력 시 사람·항목·문서·업무를 구분해 찾는다. 선택한 대상은 내부 ID로 연결하고 본문에는 배지·번호·제목이 붙은 읽기 쉬운 링크로 표시한다. 규칙: 같은 워크스페이스 안 참조 키 중복 금지, WIKI 예약, 키의 대소문자로 다른 대상을 만들지 않음, 이름·키 변경 후 기존 연결 유지, 과거 키는 별칭으로 남겨 재사용 금지, 이름이 같은 후보는 사용자가 선택. 언급했다고 담당자 지정이나 접근 권한 자동 부여를 하지 않는다. 링크·역방향 링크·멘션 알림에 원본 접근 권한을 적용한다. 프로젝트 항목과 그 안의 문서는 별도 대상이다. 문서·업무의 짧은 번호 체계는 D-48. 근거: 초안 §5, 사용자 "@는 항목 연결과 사용자 언급 모두에 사용".

### 1.4 워크스페이스 홈

- **D-19 홈 구성.** 오늘 날짜, 업무·메모·일정 빠른 추가, 실행 중인 스톱워치, 주간 달력과 가까운 일정, 기한 초과·오늘·다가오는 업무 중심의 Up Next, 중요 항목 수동 고정, 진행 중인 프로젝트·연구·스터디·강좌·취미, 최근 문서와 최근 작업, 즐겨찾기, 협업 활동과 알림. 모듈별 진행률은 해당 활동의 의미에 맞게 계산하며 업무 완료율·강의 이수율·공부 목표 달성률을 같은 방식으로 합산하지 않는다. 근거: 초안 §6.

### 1.5 멤버·권한·공유

- **D-20 역할과 기본 권한.** 관리자·작성자·독자 역할. 멤버 초대·제거·역할 변경·그룹 관리. 새 항목은 기본 비공개. 워크스페이스 공개 여부 선택 가능. 독자는 본문 읽기와 댓글 작성 가능. 재공유는 소유자 또는 공유 관리 권한자만 가능. 복제·다운로드 허용 여부는 소유자가 별도 설정. 상위 공유 권한을 기본 상속하되 문서별 비공개 예외 허용. 비로그인 공개 링크는 명시적으로 활성화하고 만료·철회 지원. 근거: 초안 §7.
- **D-21 관리자 열람.** 워크스페이스 관리자는 해당 공간의 모든 문서를 열람할 수 있다. 이 열람 범위를 사용자에게 명확히 안내한다. 근거: 초안 §7, 지침(32개 선택 2번), 사용자. 비공개 예외와의 관계는 D-40. 감사로그 열람은 D-57.
- **D-22 개인 노트.** 워크스페이스 관리자에게도 보이지 않는 개인 노트를 제공한다. 이 비공개는 앱의 워크스페이스 관리자 기준이다. 서버·DB 운영자에게도 비밀을 보장하는 암호화 요구는 확정하지 않았다(H-01, 보류). 소유 구조와 공유 규칙은 D-49, D-59. 근거: 사용자 "워크스페이스 관리자에게도 보이지 않는 개인 노트 제공", "관리자 비공개는 앱의 워크스페이스 관리자 기준이며 ... 암호화 요구와는 구분". `[대체·부분]` 초안 §21 "관리자에게 보이는 워크스페이스 문서와 진짜 개인 노트의 소유 경계": 개인 노트의 존재는 확정, 소유 구조는 D-49·D-59로 확정.
- **D-23 원본 공유와 복제.** 소유자 A는 특정 B에게 읽기 또는 수정 권한을 부여할 수 있다. B가 수정하면 A의 원본이 변경된다. 복제는 독립된 사본을 만들며 이후 원본과 자동 동기화하지 않는다. 근거: 초안 §7, 사용자.
- **D-24 워크스페이스 간 참조·공유·이동.** 포함한다. 이동 전에는 공개 범위와 권한 변화를 확인한다. 근거: 초안 §7, 사용자 "워크스페이스 간 공유·이동은 포함하기로 확정했습니다. RLS가 복잡하다는 이유로 제외하거나 다시 미정 처리하지 마세요". 검토자의 1차 제외 제안은 기각(P-R01).
- **D-25 탈퇴와 소유권.** 팀 공간에서 만든 문서는 작성자가 탈퇴해도 남고 관리자가 인계한다. 개인 소유 원본을 공유한 경우는 별도 소유권으로 처리한다. 근거: 초안 §7.
- **D-26 보호 범위의 한계 안내.** 복제·다운로드 제한으로 화면 촬영까지 방지할 수 있다고 설명하지 않는다. 근거: 초안 §7.

### 1.6 문서 편집·리비전·감사로그

- **D-27 문서 편집 경험.** Tiptap 기반 노션형 블록 편집이 기본. 블록·리치 편집, Markdown 원본 편집, 읽기 미리보기, 문서 트리·템플릿, 표·코드·수식·이미지·첨부, 댓글·멘션·공동 노트, 링크·역방향 링크, 자동 저장·저장 상태 안내, 미저장 초안 보호, **변경 이력·리비전·diff·복원**, 편집 모드 전환 시 내용 손실 방지. Markdown 문법을 알아야만 쓸 수 있는 구조로 만들지 않으며 Markdown은 추가 입력 방식이다. 실시간 공동 편집 사용 여부는 워크스페이스별로 선택하고, OFF에서도 저장 충돌을 감지하고 차이를 확인해 반영할 수 있게 한다. 위키와 모듈 문서 모두에 리비전·diff·복원을 적용한다. 근거: 초안 §8, 사용자 "위키·문서의 리비전·diff·복원 ... 확정 범위에 반드시 포함". 파일 내부 차이 분석 제외(X-03)는 업로드한 연구 파일에 관한 것이며 문서 diff와 무관하다.
- **D-28 감사로그.** 생성·삭제·이름 변경 등을 기록하는 감사로그를 이번 범위에 포함한다. 대상 이벤트·열람 권한·보존 기간은 D-57. 근거: 사용자 "생성·삭제·이름 변경 등을 기록하는 감사로그를 이번 범위에 포함합니다".
- **D-29 복원 규칙 설계.** 문서 복원과 연결된 업무·수강 진도의 상태 변경을 혼동하지 않도록 복원 규칙을 설계한다. 구체 규칙은 D-58. 근거: 사용자.

### 1.7 체크리스트

- **D-30 체크리스트 공통 입력.** 체크리스트는 에디터가 있는 화면에만 제한하지 않는다. 에디터가 없는 화면: 체크박스와 내용 입력란, 항목 추가·수정·삭제, 완료·미완료 변경. 에디터가 있는 화면: 본문 체크리스트 작성, 별도 체크리스트 입력 영역, 같은 체크리스트를 함께 보여줄 때 양쪽 수정 결과 일치. Markdown 가져오기: 붙여넣은 체크리스트에서 상태와 내용 추출, `- [ ]`는 미완료, `- [x]`는 완료, 일반 체크박스·내용 입력 영역에 채우고 사용자가 확인·수정. 문서와 별도 폼에 같은 내용을 독립적으로 중복 저장하지 않는다. 같은 체크리스트를 다루는 화면은 동일한 항목과 상태를 참조한다. 일반 체크리스트와 실제 업무·강의 진도 연결은 구분하며, 일반 체크 항목이 자동으로 업무를 생성하거나 강의를 완료시키지 않는다. 모든 체크리스트를 문서 본문에만 저장하거나 모두 업무로 만드는 것으로 해석하지 않는다. 근거: 초안 §9, 사용자. '업무로 전환'·'기존 업무·강의 회차 연결'은 제안 단계(P-10). 저장 구조·본문-폼 연결·Markdown 재가져오기 처리는 설계 대상(O-04).

### 1.8 공통 업무·일정

- **D-31 업무·일정.** 업무와 한 단계 하위 업무. 상태·우선순위·담당자·시작일·마감일. 태그·체크리스트·예상 시간. 마일스톤·선행 및 후행 관계. 반복 업무. 회의·발표·행사 일정. 목록·칸반·달력·간트. 검색·필터·정렬·저장한 보기. 일반 업무는 여러 담당자가 있어도 하나의 완료 상태를 공유한다. 강의 이수는 참여자별 상태를 유지한다. 선행 업무의 일정 변경은 영향과 충돌을 보여준 뒤 사용자가 후속 재배치를 승인한다. 미완료 반복 업무는 남겨두고 다음 회차는 원래 일정대로 생성한다. 근거: 초안 §10, 사용자 "일반 업무의 완료는 공유 상태이고 강의 이수는 사용자별 상태".

### 1.9 공통 스톱워치·시간 기록

- **D-32 시간 기록.** 모든 모듈에서 시작·일시정지·재개·종료. 업무·문서·공부·강의 회차·취미 활동에 연결. 측정 후 분류 가능. 수동 입력·수정·수정 이력·메모. 일·주·월 집계. 예상 시간과 실제 시간 비교. 사용자당 모든 워크스페이스를 통틀어 실행 중인 타이머 하나. 앱을 닫아도 측정 지속, 재접속 시 복구. 개인 시간 기록 기본 비공개, 선택한 집계만 공유. 순공부시간은 강의 시청을 제외한 능동적 공부로 정의한다. 실제 인강 수강시간·휴식시간·영상 원본 길이·배속 기준 예상 시간은 서로 구분한다. 근거: 초안 §11, 사용자.

### 1.10 모듈별 기능

- **D-33 프로젝트 모듈.** 생성·수정·복제. 키·이름·설명·아이콘·리더·멤버·그룹. 목표·범위·기간·공개 설정. 업무·하위 업무·체크리스트·담당자·우선순위. 프로젝트별 상태와 업무 설정. 마일스톤·의존 관계·반복 업무. 칸반·달력·간트. 예상·실제 작업 시간. 요구사항·설계·회의록·결정·매뉴얼·인계 문서. 산출물·완료 기준·위험·문제 기록. 회고와 재사용 템플릿. 보관·보관 해제·삭제·복구. 근거: 초안 §12.

### 1.12 이후 추가된 결정

- **D-40 관리자 열람과 문서별 비공개의 관계.** 워크스페이스 관리자는 해당 공간의 비공개 문서도 열람한다. 문서별 비공개 예외(D-20)는 일반 멤버에게 적용된다. 관리자에게도 비공개인 개인 노트(D-22)는 별도 영역·권한으로 처리한다. 근거: 사용자 "O-21은 해소한다. 워크스페이스 관리자는 해당 공간의 비공개 문서도 열람한다". O-21 `[해소]`.
- **D-41 휴지통 보존 기간.** 휴지통 기본 보존 기간은 30일이며 관리자가 설정할 수 있다. 근거: 지침(32개 선택 9번), 사용자 "휴지통 기본 보존 기간 30일과 관리자 설정 가능을 확정 결정에 추가한다". 최초 작성 시 누락되었던 항목이다(7절 변경 이력).
- **D-42 품질 검사 검증 기록 방식.** 개발 지침의 설정은 저장소 초기화 단계에서 구현한다. 설정이 실제로 위반을 잡는지 확인한 기록은 실행 명령·대상 커밋 SHA·결과·필요한 실패 로그를 PR이나 작업 보고에 남기는 것을 기본안으로 한다. 별도 증거 프레임워크를 만들지 않는다. 근거: 사용자 "검증 기록은 실행 명령·대상 SHA·결과·필요한 실패 로그를 PR이나 작업 보고에 남기는 기본안으로 정리한다". O-24 `[해소]`.
- **D-43 열린 항목의 처리 방식.** 열린 항목은 사용자 결정과 기술 설계로 나눈다. 기술 설계는 검토자가 근거·권장안·대안을 제시하고 구현 시 진행하며 무조건 사용자에게 선택을 넘기지 않는다. 기능 축소·권한 확대·새 서비스나 비용 추가는 사용자 결정으로 남긴다. 근거: 사용자.
- **D-45 인증 방식: OIDC 전용.** 인증은 OIDC 전용으로 한다. Keycloak을 기준 제공자로 연동·검증하되 Keycloak 전용 API에 불필요하게 의존하지 않고 표준 OIDC를 사용한다. 사용자 로그인·자격 증명·비밀번호 복구·MFA는 인증 제공자가 담당한다. fvoci는 앱 세션·사용자 프로필·워크스페이스 초대·멤버십·역할·문서 권한을 담당한다. OIDC 로그인 성공만으로 모든 워크스페이스 접근 권한을 부여하지 않는다. 사용자 식별은 이메일이 아니라 발급자(issuer)와 subject의 조합을 기준으로 하며, 같은 이메일이라는 이유로 계정을 자동 병합하지 않는다. 개발·통합 테스트에서는 격리된 Keycloak 환경으로 로그인·세션 만료·로그아웃·권한 거부를 검증한다(D-10의 컨테이너 목록에 추가). 셀프호스트 초기 관리자 지정과 초대 수락 절차는 D-51. Keycloak을 배포에 필수 포함할지 외부 OIDC 서버를 연결할지는 배포 설계에서 구분한다(O-25). 자체 비밀번호 로그인·복구와 SAML은 제외한다(X-09). 근거: 지침(인증 방식 전달 문구) "인증 방식을 OIDC 전용으로 확정한다". O-13 `[해소]`.
- **D-46 저장소 초기 구조 기준.** 2026-10-17 전달받은 디렉터리 구조(`docs/repo-structure.md`)를 fvoci의 초기 구조 기준으로 승인한다. 예시의 빈 폴더와 파일을 모두 미리 만들 필요는 없으며 구현에 필요한 순서대로 만든다. 개발 지침 파일명은 `docs/development.md`로 통일하고 이전 파일과 중복 유지하지 않는다. 이 승인은 구조 기준과 문서 정리에 한정하며 제품 구현 착수 승인은 별도다. 근거: 사용자 "전달한 디렉터리 구조를 fvoci의 초기 구조 기준으로 승인한다". C-02 `[해소]`.
- **D-47 사용자 결정과 구현 선택의 경계.** 사용자 결정이 필요한 것은 기능 범위·권한·삭제 및 보존 정책·비용·외부 서비스 추가처럼 제품에 영향을 주는 사항이다. 파일명·폴더 배치·lint 설정·검증 결과 기록 방식은 승인된 원칙 안에서 검토자가 판단하고 변경 이유만 간단히 기록한다. 명시적으로 확정한 요구와 기술 구현 선택을 구분하되, 모든 구현 선택을 사용자 승인 대기로 만들지 않는다. D-43을 구체화한다. 근거: 사용자.
- **D-48 번호 체계.** 모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유한다. DEV-1, DEV-2를 각각 무엇이 차지하든 중복되지 않는다. 화면에서는 유형 아이콘과 제목을 표시한다. 근거: 사용자 "모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유합니다". O-01 `[해소]`. P-03 채택.
- **D-49 개인 노트 공유.** 개인 노트는 기본 비공개이되 소유자가 특정 사람에게 읽기·수정 권한을 줄 수 있다. 공유해도 개인 소유는 유지되고, 상대방의 워크스페이스 관리자에게 권한이 따라가지 않는다. 기존 원본 공유 방식(D-23)과 일치한다. 근거: 사용자. O-02 `[해소]`. P-04 `[기각]`.
- **D-50 시간대 규칙.** 정확한 시각은 UTC 기준으로 저장하고 사용자 시간대로 표시한다. 날짜만 있는 일정은 날짜 그대로 보존한다. 개인 시간 집계는 사용자 시간대, 공동 반복 일정은 일정에 지정한 시간대를 기준으로 한다. 근거: 사용자. O-05 `[해소]`.
- **D-51 계정·초대·인계·삭제·초기 관리자.** OIDC 로그인 후 초대를 수락한다. 초대 대상 확인 없이 링크 소지만으로 가입시키지 않는다. 마지막 소유자는 인계 없이 탈퇴할 수 없고, 소유권 인계는 수신자 수락으로 완료한다. 워크스페이스 삭제는 소유자만 가능하며 확인 후 휴지통으로 보낸다(보존 기간은 D-41). 초기 관리자는 운영자가 지정한 OIDC 식별자로 설정하고 "첫 로그인 사용자 자동 관리자"는 사용하지 않는다(X-10). 근거: 사용자. O-06 `[해소]`.
- **D-52 운영 한도.** 파일 하나의 최대 크기·워크스페이스 총 저장량·업로드 동시성·알림 발송률을 설정 가능하게 한다. 구체적인 기본값은 예상 사용량과 테스트 결과로 검토자가 제안하며(O-26), 코드에 임의의 고정값을 박지 않는다. 근거: 사용자. O-07 `[해소]`.

- **D-60 의존성 라이선스 정책.** 상업 이용·수정·재배포·SaaS 운영에 적합한 허용적 라이선스를 우선한다. MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, PostgreSQL License를 기본 허용 후보로 두되 실제 사용할 버전·구성요소의 조건을 확인한다. 직접·전이 의존성, 복사해 온 코드, WASM·폰트·아이콘도 확인한다. GPL·AGPL·LGPL·MPL 등 카피레프트, SSPL·BUSL·비상업용·사용 목적 제한·상용 계약 필수·라이선스 불명 구성요소는 자동 도입하지 않고 조건과 대안을 보고해 별도 승인받는다. 이중 라이선스는 허용되는 쪽을 선택할 수 있는지 확인하고 근거를 기록한다. 오픈소스 코어와 유료·Enterprise 확장을 구분하며 저장소에 MIT 파일이 있다는 이유로 전체 기능을 MIT로 간주하지 않는다. Docker 분리로 의무가 사라진다고 판단하지 않고 앱 포함 코드·별도 서비스·배포 이미지 OS 패키지를 구분해 검토한다. 저작권 고지·라이선스 원문·NOTICE를 배포물에 보존한다. 설치 버전을 고정하고 의존성 변경 시 라이선스 검사를 수행하며 기존 Cargo·pnpm 도구를 활용하고 새 검사 프레임워크는 만들지 않는다. 현재 선택한 rhwp·Meilisearch·Tiptap과 Office 뷰어 후보도 실제 사용할 패키지·버전·기능 범위로 확인하고, 조건이 충돌하면 조용히 대체하거나 예외 처리하지 않고 보고한다(O-28). fvoci 자체의 공개 라이선스는 별도 결정이다(O-27). 전문은 `docs/development.md` 7절. 근거: 지침(의존성 라이선스 전달 문구).
- **D-61 S3 호환 저장소 대상.** 운영 S3 호환 저장소는 Cloudflare R2를 우선 대상으로 한다. 로컬·CI 테스트 저장소는 SeaweedFS의 고정 버전 이미지를 우선 검토한다(LICENSE 확인: Apache-2.0). 라이선스와 필요한 S3 API 호환성(multipart·완료·중단·재개)을 확인하고, 테스트용 독립 버킷·볼륨으로 격리한다. 자체 S3 서버는 구현하지 않는다. 로컬 검사 성공을 R2 검증 완료로 간주하지 않으며, 실제 R2 연결·자격 증명·비용이 필요한 검증은 별도로 요청받는다. 기존 로컬 파일 저장소 지원은 유지한다. 근거: 사용자. - **D-64 CI 구조 원칙.** CI는 공통 베이스 이미지와 저장소의 표준 명령을 재사용한다. 기존 `deploy/docker/dev.Dockerfile`을 베이스로 쓰고 Rust·Node·pnpm·검사 도구·시스템 의존성을 고정 버전으로 제공한다. 베이스 이미지는 Dockerfile·도구 버전·시스템 의존성이 바뀔 때와 보안 업데이트 주기에만 갱신하고 제품 커밋마다 만들지 않는다. 후속 job은 같은 이미지 digest를 쓰고 latest에 의존하지 않는다. CI YAML은 트리거·권한·job 의존·공통 명령 호출·결과 업로드만 담당하며 설치·판정 로직을 긴 셸 블록으로 쓰지 않는다. 로컬과 CI는 같은 xtask·pnpm 명령을 쓴다. 베이스 이미지에 제품 소스·시크릿·실행 중 DB를 넣지 않고 PostgreSQL·Meilisearch·테스트 저장소는 별도 컨테이너로 격리한다. 제품 바이너리·웹 빌드는 공유 가능하면 한 번 만들어 소스 SHA·아키텍처·빌드 옵션이 맞는 것만 소비한다. 의존성 캐시는 속도용이며 없어도 빌드·검증이 된다. 현재 규모에서는 단순한 job으로 시작하고 병목 측정 전 샤딩·matrix·범용 실행 프레임워크를 만들지 않는다. 이미지 배포 승인 전에는 로컬 빌드까지만 준비한다. 근거: 지침(CI 구조 전달 문구). 구현은 `.github/workflows/{base-image,ci}.yml`, 설명은 `docs/development.md` 10절.

- **D-66 프론트엔드 UI 구성.** 기본 UI는 shadcn-svelte(기반 Bits UI)를 쓰고 스타일은 Tailwind CSS와 공통 디자인 토큰으로 관리한다. 문서 편집기는 Tiptap(D-27). Skeleton 등 다른 종합 UI 시스템을 병행 도입하지 않는다. 업무 달력·간트·칸반 드래그는 별개로 필요 시 기존 구현을 조사하며, 날짜 선택 컴포넌트를 업무 달력 구현으로 보지 않는다. 도입: 현재 Svelte·Vite·TypeScript 구성과 호환되는 공식 방식(Vite 수동 설치)으로, SvelteKit·SSR로 전환하지 않는다. 최초 도입은 현재 화면에 필요한 구성요소(버튼·입력란·체크박스·라벨·대화상자·메뉴·사이드바)로 제한한다. 공통 UI는 `apps/web/src/lib/ui`에 모으고 기능별 코드에서 복사하지 않는다. CLI 기본 경로 대신 별칭(`$lib/ui`)으로 기존 구조에 맞춘다. 재사용·수정: 기본 동작·접근성·키보드 처리는 제공 구현을 우선 쓰고, 디자인 수정은 색·글자·간격·모서리·포커스 토큰 중심으로 한다. 실제 요구 없는 커스텀 래퍼·범용 폼 엔진·자체 모달·메뉴·포커스 관리자를 만들지 않는다. 가져온 컴포넌트의 출처·버전·명령을 `apps/web/src/lib/ui/README.md`에 기록하고 수정분을 최소화한다. 라이브러리 사용이 접근성 검증을 대신하지 않는다. 가독성: 글자 크기는 rem 기반, 브라우저 기본 크기와 확대 설정 존중, CJK 본문·입력란·목록의 공통 타이포그래피와 줄 높이 토큰, 키보드 이동·보이는 포커스·라벨·오류 안내·대화상자 종료 후 포커스 복귀 확인, 색상 배지 외 이름·아이콘 병행. 일반 체크리스트는 에디터 없는 화면에서도 체크박스와 입력란으로 쓰고 문서 편집기와 같은 데이터·권한 규칙을 따른다(D-30). 범위: 공통 UI 기반 선택과 최소 도입이며 전체 화면 개편·새 기능 추가가 아니다. 근거: 지침(프론트엔드 UI 전달 문구). 도입 기록은 `docs/development.md` 11절.
- **D-67 개발 도구 사용 원칙.** 저장소 검색은 rg, 파일 목록은 `rg --files`를 우선 쓰고 경로·유형을 좁힌다. rg는 숨김·ignore 파일을 제외하므로 결과가 없다는 것만으로 파일이나 호출자가 없다고 단정하지 않으며 필요할 때만 `--hidden`·`--no-ignore`를 쓴다. Git 추적 파일만 볼 때는 git grep, 간단한 파이프 필터는 grep. JSON은 jq 등 구조화된 도구로 처리하고 코드 변경은 문맥을 확인한 패치로 한다. 셸 안에서 Python 코드를 생성하는 임시 헬퍼로 파일을 수정하지 않는다. 설치된 도구는 PATH의 짧은 명령으로 호출하되 저장소 고정 버전을 따르고 절대 경로·래퍼·중복 설치를 추가하지 않는다. 도구가 없으면 기존 도구로 가능한지 먼저 판단하고 도구 정비를 대규모 작업으로 키우지 않는다. 근거: 지침(개발 도구 사용 원칙 전달 문구). `AGENTS.md`에 반영.
- **D-44 보류 항목의 취급.** 운영자 대상 암호화(H-01)와 외부 플랫폼 자동 시청 추적(H-02)은 현재 필수 범위의 차단 항목이 아니다. 새 승인이 없는 상태에서 구현 범위를 확대하지 않는다. 근거: 사용자 "현재 필수 범위의 차단 항목에서 분리한다. 새 승인이 없는 상태에서 구현 범위를 확대하지 않는다".

## 3. 열린 항목

### 3.1 사용자 결정

공개·공유·삭제·보존·권한·사용 경험·비용에 영향을 주는 정책. 기술 설계 진행 중 기능 축소·권한 확대·새 서비스·비용 추가가 생기면 여기에 새 번호로 올린다.

- **O-30** 라이선스 허용 목록 추가 승인. 2026-10-17 초기화의 최소 의존성만으로도 허용 목록 밖 라이선스가 나왔다. 모두 허용적 또는 공개 도메인 계열이며 카피레프트는 MPL-2.0(파일 단위, 빌드 도구) 하나다. 검토자는 예외를 넣지 않았고 `cargo xtask check`는 이 항목 때문에 FAIL 상태다. 표는 `docs/development.md` 9절. 선택지: 목록에 추가 승인, 또는 대안 의존성 교체 지시.
- **O-27** fvoci 자체를 어떤 라이선스로 공개할지. 의존성 정책(D-60)과 별도. 지침(의존성 라이선스 전달 문구) "fvoci 자체를 어떤 라이선스로 공개할지는 의존성 정책과 별도로 결정한다". 검토자 권장안은 제시하지 않는다. 제품·사업 결정이다. 사용자 "fvoci 자체 라이선스는 나중에 결정합니다"에 따라 열린 채로 두며, 공개 전까지 결정하면 된다. 구현의 차단 항목은 아니다.

### 3.2 기술 설계

확정된 정책을 구현하는 선택. 검토자가 근거·권장안·대안을 제시하고 구현 시 권장안으로 진행하며 결과를 기록한다. 진행 중 기능 축소·권한 확대·새 서비스·비용 추가가 생기면 3.1로 올린다.

- **O-04** 체크리스트의 저장 구조, 본문과 폼의 연결 방식, Markdown 재가져오기 시 추가·교체 처리. 초안 §9, §21.
  - 근거: D-30은 같은 체크리스트를 어느 UI에서 다뤄도 동일 항목·상태를 참조하라고 요구한다.

  - 대안: 본문 블록을 정본으로 두고 폼은 본문을 파싱해 보여준다. 에디터 없는 화면에서 본문을 수정해야 하므로 권장하지 않는다.
