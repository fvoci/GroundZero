# fvoci 결정 기록

작성일: 2026-10-17
상태: 기획 단계. 제품 코드 구현 전. 저장소 초기화 전.

## 이 문서의 사용법

항목은 다섯 범주로 나눈다. 범주를 섞지 않는다.

| 접두어 | 범주        | 뜻                                                                                    |
| ------ | ----------- | ------------------------------------------------------------------------------------- |
| D      | 확정 결정   | 사용자가 명시적으로 확정한 사항. 근거로 사용자 발언 또는 기획 초안의 절 번호를 남긴다 |
| P      | 미승인 제안 | 검토자가 제안했으나 사용자가 승인하지 않은 사항. 결정이 아니다                        |
| O      | 열린 항목   | 실제로 결정이 필요한데 아직 정하지 않은 사항                                          |
| X      | 범위 제외   | 이번 범위에서 빼기로 한 사항                                                          |
| C      | 확인 필요   | 원문을 확인할 수 없어 해석을 보류한 사항                                              |

표기 규칙

- 근거는 세 종류로 구분한다.
  - `초안 §n`: 2026-10-17 전달받은 "통합 작업·지식·학습 관리 앱 — 전체 기획 초안"의 절 번호. 전달받은 지침이다.
  - `지침`: 초안 외에 문서 형태로 전달받은 지침. 품질 기준 문구, Docker Compose 추가 전달 문구, 32개 선택 목록.
  - `사용자`: 대화에서 사용자가 직접 한 발언. 인용은 짧게 남긴다.
- 열린 항목은 두 종류로 나눈다. **사용자 결정**은 공개·공유·삭제·보존·권한·사용 경험·비용에 영향을 주는 정책이다. **기술 설계**는 확정된 정책을 구현하는 저장 구조·라이브러리·검사 설정·실행 구조이며, 검토자가 근거·권장안·대안을 제시하고 구현 시 진행한다. 단, 기능 축소·권한 확대·새 서비스나 비용 추가가 생기면 사용자 결정으로 올린다.
- `[대체]`: 이전 결정이나 초안의 미정 항목을 새 결정이 대체했다는 표시. 이전 내용을 함께 남긴다.
- `[기각]`: 검토자 제안을 사용자가 거부했다는 표시.
- `[해소]`: 열린 항목이 결정으로 닫혔다는 표시. 닫은 결정 번호를 남긴다.
- 검토자의 추천은 사용자 결정으로 바꾸지 않는다. 확정한 사항을 다시 미정으로 돌리지 않는다.
- 근거 없는 일정 추정은 기록하지 않는다.

## 0. 이해 요약

검토자가 정리하고 사용자가 "전반적으로 맞습니다"로 확인한 내용이다. 예시는 이해 확인용이며, 아직 정하지 않은 데이터 구조를 확정 사실로 쓰지 않는다.

fvoci는 빈 저장소에서 새로 만드는 통합 작업·지식·학습 관리 앱이다. 한 번 입력한 정보를 여러 화면에서 다시 쓰는 것이 핵심 원칙이고, 셀프호스트를 먼저 완성하되 SaaS를 함께 고려한다. Rust 백엔드, Svelte 프론트엔드, Tiptap 기반 블록 편집, CRDT 공동 편집, Meilisearch 검색, PostgreSQL 단일 DB가 기본 방향이다.

### 예시 1. 워크스페이스 → 모듈 인스턴스 → 항목·문서·업무

워크스페이스 A 안에 프로젝트 유형 모듈을 두 개 만들 수 있다. 하나는 이름 "개발", 키 DEV이고 다른 하나는 이름 "운영", 키 OPS다. 둘 다 유형은 프로젝트이며 내부 기능은 같다. DEV 모듈 안에는 개별 프로젝트 항목이 있고, 그 항목 안에 업무·문서·체크리스트·시간 기록이 붙는다. `@A/DEV-1`은 DEV 모듈 범위의 1번을 가리키며, 모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유하므로 DEV-1이 항목이면 DEV-2는 업무일 수 있다. 화면에서는 유형 아이콘과 제목으로 구분한다(D-48). 공용 위키는 모듈이 아니라 워크스페이스 직속이며 키 WIKI로 참조한다. 번호는 모듈 인스턴스마다 따로 증가하므로 DEV-1과 OPS-1은 다른 대상이다.

### 예시 2. 개인 노트와 관리자 열람

워크스페이스 A의 관리자는 A 안의 모든 문서를 열람할 수 있고, 멤버가 문서별로 비공개 설정한 문서도 포함된다(D-40). 반면 사용자 영환이 쓰는 개인 노트는 A의 관리자에게도 보이지 않는다. 그래서 개인 노트는 워크스페이스 소속 문서와는 다른 소유 구조여야 하는데, 개인 노트는 사용자 소유로 별도 관리하며 기본 비공개이고, 소유자가 특정 사람에게 읽기·수정 권한을 줄 수 있다. 공유해도 개인 소유는 유지되고 상대방의 워크스페이스 관리자에게 권한이 따라가지 않는다(D-49, D-59). 이 비공개는 앱의 권한 수준이며, 서버나 DB 운영자가 내용을 읽을 수 없게 하는 암호화는 확정한 요구가 아니다(H-01, 보류).

### 예시 3. 체크리스트의 여러 입력 방식

어떤 업무의 상세 화면에 에디터가 없더라도 체크박스와 내용 입력란이 있어 항목을 추가·완료할 수 있다. 문서 편집 화면에서는 본문 안에 체크리스트 블록을 쓸 수도 있고, 별도 체크리스트 입력 영역을 쓸 수도 있다. 사용자가 `- [x] 자료 수집`과 `- [ ] 초안 작성`을 붙여넣으면 두 항목이 완료·미완료 상태로 입력 영역에 채워지고 사용자가 확인·수정한다. 한 화면에 같은 체크리스트가 본문과 입력 영역 양쪽에 보이면 어느 쪽에서 바꿔도 결과가 같아야 한다. 체크 항목이 자동으로 업무가 되거나 강의를 완료시키지는 않는다. "업무로 전환"과 "기존 업무·강의 회차 연결"은 아직 제안 단계다(P-10). 체크리스트를 어디에 저장하고 어떻게 연결하는지는 설계 대상이다(O-04).

### 예시 4. 연구 파일 버전 관리

연구 항목에 `survey.csv`를 올리면 v1이 된다. 정제 후 같은 자료에 새 파일을 올리면 v2가 추가되고 v1은 남는다. 각 버전에는 업로더·시각·변경 설명이 기록된다. 분석 기록 "회귀분석 1차"는 데이터 v1과 코드·결과 파일의 특정 버전을 연결한다. 이후 v3이 올라와도 "회귀분석 1차"는 v1을 가리킨다. 이전 버전은 열람·다운로드할 수 있다. 앱은 코드를 실행하지 않고, 업로드한 파일 내부의 차이 분석이나 실험 자동 추적도 하지 않는다. 앱에서 작성한 문서의 리비전·diff·복원은 별개이며 확정 범위다(D-27).

## 1. 확정 결정

### 1.1 제품·기술

- **D-01 신규 개발, 이름 fvoci.** 빈 저장소에서 새로 시작한다. 근거: 사용자 "빈 저장소에서 신규 개발, 이름은 fvoci". `[대체]` 초안 §2 "기존 FVOCI의 확장인지 별도 앱인지 ... 별도로 확정한다".
- **D-02 PostgreSQL만 지원.** 근거: 사용자 "PostgreSQL만 지원". `[대체]` 초안 §2 "최종 DB 지원 범위는 별도로 확정한다".
- **D-03 기본 기술 구성.** 백엔드 Rust, 개발·빌드·검증 명령 Rust xtask, 프론트엔드 Svelte, 패키지 관리 pnpm, 편집기 Tiptap(노션형 블록 편집), 공동 편집 CRDT. 근거: 초안 §2, 사용자 "Rust + xtask + Svelte + pnpm + Tiptap + CRDT가 기본 방향".
- **D-04 검색과 HWP 뷰어.** 검색은 Meilisearch. HWP/HWPX 뷰어는 rhwp 기준. rhwp의 형식별 실제 호환성은 검증 대상이다(O-11). 근거: 초안 §2, 사용자.
- **D-05 미리보기 범위.** PDF·이미지·텍스트·Office·HWP/HWPX 읽기 미리보기를 포함한다. Office·HWP 본문 편집과 수정본 저장은 제외한다(X-01). Office 미리보기 엔진은 비교 평가 후 선택한다(D-54, O-10). 근거: 초안 §17, 사용자.
- **D-06 파일 저장과 업로드.** S3 호환 또는 서버 로컬 스토리지. 청크 업로드·재개·재시도·무결성 확인. 완료 요청 중복 처리 방지. 취소·만료 업로드의 잔여 데이터 정리. 파일 다운로드 권한 확인. Cloudflare 경유 시 개별 요청 크기 제한 안에서 전송하고, 완료 단계에서 파일 전체를 거대한 요청으로 다시 전송하지 않는다. 최대 파일 크기·총 저장량은 운영 설정으로 관리한다(D-52). 근거: 초안 §2, §17.
- **D-07 셀프호스트 우선, SaaS 고려, 공개 시점.** 셀프호스트를 먼저 완성하고 SaaS 운영을 함께 고려한다. 합의한 전체 기능을 갖춘 뒤 공개한다. 내부 구현·검증은 작은 사용자 흐름부터 단계적으로 한다. 전체 기능 공개 목표가 한 번에 모든 코드를 작성해야 한다는 뜻은 아니다. 근거: 초안 §1, 사용자 "합의된 전체 기능을 갖춘 뒤 공개하되 내부 구현·검증은 단계적으로".
- **D-08 SaaS·격리·운영 원칙.** 데이터의 소유 워크스페이스를 명확히 기록한다. 워크스페이스 간 공유는 명시적인 권한으로 처리한다. 관리자 열람은 자기 워크스페이스 범위에 한정한다. 개인 시간 기록의 비공개 정책을 별도로 유지한다. PostgreSQL RLS와 앱 권한 검사를 함께 설계한다(세부 정책 O-09). 앱 실행 역할과 운영·마이그레이션 역할을 분리한다. 검색·첨부·캐시·실시간 연결·백그라운드 작업에도 격리를 적용한다. 셀프호스트와 SaaS에서 핵심 데이터와 권한의 의미를 일치시킨다. 근거: 초안 §19.
- **D-09 Rust·TypeScript 품질 기준.** rustfmt·Clippy 필수, 고정 툴체인에서 CI 경고를 오류로 처리, 제품 코드의 무분별한 unwrap·expect·panic 금지, 오류 버림 금지, 자체 코드 unsafe 기본 금지, 의미 있는 타입, async 책임 명시, Clippy 규칙 선택적 활성화. TypeScript strict와 명시 옵션, svelte-check, 타입 정보 기반 ESLint, unknown에서 시작하는 외부 데이터 검증, any·이중 단언·@ts-ignore 금지, 비동기 오류·취소·오래된 응답 처리, 수명주기 해제. Rust↔TypeScript 계약 단일화와 런타임 검증, 전송 표현 결정, 상태 정본 명시. 검사·예외 규칙과 복잡도 원칙. 전문은 `docs/development.md`. 현재는 문서화 단계이며 코드 초기화 단계에서 실제 설정과 검증 명령으로 강제한다. 근거: 지침(품질 기준 문구) "fvoci의 Rust·TypeScript 품질 기준을 결정 기록과 개발 지침에 추가한다".
- **D-10 Docker Compose 개발·통합 테스트 환경.** PostgreSQL·Meilisearch·테스트용 S3 호환 저장소를 컨테이너로 실행한다. D-45에 따라 격리된 Keycloak도 테스트 컨테이너에 포함한다. 운영 서비스나 개인 개발 DB를 테스트에 쓰지 않는다. 이미지·Compose·의존성 버전을 저장소에서 관리하고 로컬과 CI가 같은 이미지와 검사 명령을 쓴다. 빌드 이미지와 실행 이미지 분리, 병렬 실행 격리, UID/GID 검증, 시크릿 분리, privileged·Docker 소켓·호스트 전체 마운트 금지, 동시 실행 수 제한, 자기 자원만 정리, 호스트 도구 허용 범위, xtask·pnpm 진입점. 전문은 `docs/development.md`. 현재는 문서화 단계이며 저장소 초기화 단계에서 실제 설정을 구현한다. 근거: 지침(추가 전달 문구) "개발·통합 테스트 환경은 Docker Compose를 기준으로 구성한다".

### 1.2 제품 목적과 구현 원칙

- **D-11 제품 목적.** 프로젝트·연구·스터디·강의·취미에서 발생하는 업무·문서·일정·자료·시간 기록을 한곳에서 관리한다. 여러 서비스에 같은 내용을 반복 입력하는 불편을 줄인다. 입력한 정보를 한눈에 보고 빠르게 찾는다. 문서·업무·자료·사람을 연결한다. 개인 사용자와 소규모 팀을 모두 지원한다. 혼자 사용할 때 불필요한 협업 절차를 강제하지 않는다. Plane·Kaneo·Outline의 유용한 경험을 참고한다. 근거: 초안 §1.
- **D-12 구현 원칙.** 동일한 정보는 한 번 입력하고 여러 화면에서 재사용한다. 같은 상태를 문서·폼·업무 DB에 독립적으로 중복 관리하지 않는다. UI의 체크 표시와 실제 저장 성공을 구분한다. 읽기 권한과 수정·복제·다운로드 권한을 구분한다. 실패·재시도·동시 편집·권한 철회·복구 상황도 검증한다. 공통 기능을 모듈마다 별도로 재구현하지 않는다. 사용자에게 Markdown이나 내부 ID 이해를 요구하지 않는다. 공개 범위는 이번 합의 목록으로 고정하고 추가 아이디어는 후속 목록으로 관리한다(X-08). 근거: 초안 §20.

### 1.3 구조·명칭

- **D-13 워크스페이스.** 사람·권한·콘텐츠를 묶는 공간. 한 사용자는 여러 워크스페이스에 속할 수 있다. 워크스페이스 안에는 홈, 위키, 프로젝트·연구·스터디·강의·취미 모듈, 검색·내 업무·최근 항목·즐겨찾기·알림을 둔다. 근거: 초안 §3.
- **D-14 용어.** 위키 = 워크스페이스 공용 지식 공간. 문서 = 위키 또는 모듈 안에서 작성하는 콘텐츠. 모듈 = 프로젝트·연구·스터디·강의·취미라는 기능 유형. 항목 = 개별 프로젝트·연구·스터디·강좌·취미 활동. 목록 = 항목을 모아 탐색하는 화면. 보기 = 목록·칸반·달력·간트 등 표현 방식. 워크플로 = 업무 상태와 전환 과정. 모듈 내부는 '프로젝트 위키'가 아니라 '프로젝트 문서', '연구 문서'로 부른다. 근거: 초안 §3, 사용자.
- **D-15 다섯 유형과 모듈 복수 생성.** 프로젝트·연구·스터디·강의·취미의 다섯 유형을 제공한다. 같은 유형의 모듈도 DEV·OPS처럼 여러 개 만들 수 있다. 근거: 사용자 "같은 유형의 모듈을 DEV·OPS처럼 여러 개 생성 가능". `[대체]` 초안 §21 "같은 유형의 모듈을 여러 개 만들 수 있는지, 이름만 바꾸는지".
- **D-16 모듈 이름.** 모듈의 표시 이름은 사용자가 정한다. 내부 기능 유형은 이름 변경과 무관하게 유지한다. 근거: 초안 §4.
- **D-17 ID·배지·번호.** 워크스페이스 내부 ID는 UUIDv7. 워크스페이스 표시 이름 중복 허용. 이름이 같은 공간은 색상 배지·아이콘·보조 정보로 구분하고, 배지 색상은 자동 지정 또는 사용자 선택. 권한 검사와 참조는 내부 ID로 처리. 각 항목에 변하지 않는 내부 고유 ID. 사람이 보는 번호는 워크스페이스·모듈 범위에서 원자적으로 증가. 삭제된 번호 재사용 금지. 번호 사이 빈 번호 허용. 정렬·이름 변경으로 재매김하지 않음. 요청 재시도로 중복 생성 금지. 동일 유형 모듈이 여러 개이므로 번호 범위는 모듈 인스턴스를 구분해 설계한다. 번호가 세는 대상은 D-48. 근거: 초안 §4, 사용자 "번호 범위는 모듈 인스턴스를 구분해 설계해야 합니다".
- **D-18 @ 링크와 사용자 언급.** 공용 위키의 참조 키는 WIKI. 모듈은 사용자 지정 이름과 짧은 참조 키를 분리한다. 예: `@A/DEV-1`, `@A/LAB-1`, `@A/CLASS-1`, `@A/WIKI-1`, 사용자 언급 `@영환`. @ 입력 시 사람·항목·문서·업무를 구분해 찾는다. 선택한 대상은 내부 ID로 연결하고 본문에는 배지·번호·제목이 붙은 읽기 쉬운 링크로 표시한다. 규칙: 같은 워크스페이스 안 참조 키 중복 금지, WIKI 예약, 키의 대소문자로 다른 대상을 만들지 않음, 이름·키 변경 후 기존 연결 유지, 과거 키는 별칭으로 남겨 재사용 금지, 이름이 같은 후보는 사용자가 선택. 언급했다고 담당자 지정이나 접근 권한 자동 부여를 하지 않는다. 링크·역방향 링크·멘션 알림에 원본 접근 권한을 적용한다. 프로젝트 항목과 그 안의 문서는 별도 대상이다. 문서·업무의 짧은 번호 체계는 D-48. 근거: 초안 §5, 사용자 "@는 항목 연결과 사용자 언급 모두에 사용".

### 1.4 워크스페이스 홈

- **D-19 홈 구성.** 오늘 날짜, 업무·메모·일정 빠른 추가, 실행 중인 스톱워치, 주간 달력과 가까운 일정, 기한 초과·오늘·다가오는 업무 중심의 Up Next, 중요 항목 수동 고정, 진행 중인 프로젝트·연구·스터디·강좌·취미, 최근 문서와 최근 작업, 즐겨찾기, 협업 활동과 알림. 모듈별 진행률은 해당 활동의 의미에 맞게 계산하며 업무 완료율·강의 이수율·공부 목표 달성률을 같은 방식으로 합산하지 않는다. 근거: 초안 §6.

### 1.5 멤버·권한·공유

- **D-20 역할과 기본 권한.** 관리자·작성자·독자 역할. 멤버 초대·제거·역할 변경·그룹 관리. 새 항목은 기본 비공개. 워크스페이스 공개 여부 선택 가능. 독자는 본문 읽기와 댓글 작성 가능. 재공유는 소유자 또는 공유 관리 권한자만 가능. 복제·다운로드 허용 여부는 소유자가 별도 설정. 상위 공유 권한을 기본 상속하되 문서별 비공개 예외 허용. 비로그인 공개 링크는 명시적으로 활성화하고 만료·철회 지원. 근거: 초안 §7.
- **D-21 관리자 열람.** 워크스페이스 관리자는 해당 공간의 모든 문서를 열람할 수 있다. 이 열람 범위를 사용자에게 명확히 안내한다. 근거: 초안 §7, 지침(32개 선택 2번), 사용자. 비공개 예외와의 관계는 D-40. 감사로그 열람은 D-57.
- **D-22 개인 노트.** 워크스페이스 관리자에게도 보이지 않는 개인 노트를 제공한다. 이 비공개는 앱의 워크스페이스 관리자 기준이다. 서버·DB 운영자에게도 비밀을 보장하는 암호화 요구는 확정하지 않았다(H-01, 보류). 소유 구조와 공유 규칙은 D-49, D-59. 근거: 사용자 "워크스페이스 관리자에게도 보이지 않는 개인 노트 제공", "관리자 비공개는 앱의 워크스페이스 관리자 기준이며 ... 암호화 요구와는 구분". `[대체·부분]` 초안 §21 "관리자에게 보이는 워크스페이스 문서와 진짜 개인 노트의 소유 경계": 개인 노트의 존재는 확정, 소유 구조는 D-49·D-59로 확정.
- **D-23 원본 공유와 복제.** 소유자 A는 특정 B에게 읽기 또는 수정 권한을 부여할 수 있다. B가 수정하면 A의 원본이 변경된다. 복제는 독립된 사본을 만들며 이후 원본과 자동 동기화하지 않는다. 근거: 초안 §7, 사용자.
- **D-24 워크스페이스 간 참조·공유·이동.** 포함한다. 이동 전에는 공개 범위와 권한 변화를 확인한다. 근거: 초안 §7, 사용자 "워크스페이스 간 공유·이동은 포함하기로 확정했습니다. RLS가 복잡하다는 이유로 제외하거나 다시 미정 처리하지 마세요". 검토자의 1차 제외 제안은 기각(P-R01).
- **D-25 탈퇴와 소유권.** 팀 공간에서 만든 문서는 작성자가 탈퇴해도 남고 관리자가 인계한다. 개인 소유 원본을 공유한 경우는 별도 소유권으로 처리한다. 근거: 초안 §7.
- **D-26 보호 범위의 한계 안내.** 복제·다운로드 제한으로 화면 촬영까지 방지할 수 있다고 설명하지 않는다. 근거: 초안 §7.

### 1.6 문서 편집·리비전·감사로그

- **D-27 문서 편집 경험.** Tiptap 기반 노션형 블록 편집이 기본. 블록·리치 편집, Markdown 원본 편집, 읽기 미리보기, 문서 트리·템플릿, 표·코드·수식·이미지·첨부, 댓글·멘션·공동 노트, 링크·역방향 링크, 자동 저장·저장 상태 안내, 미저장 초안 보호, **변경 이력·리비전·diff·복원**, 편집 모드 전환 시 내용 손실 방지. Markdown 문법을 알아야만 쓸 수 있는 구조로 만들지 않으며 Markdown은 추가 입력 방식이다. 실시간 공동 편집 사용 여부는 워크스페이스별로 선택하고, OFF에서도 저장 충돌을 감지하고 차이를 확인해 반영할 수 있게 한다. 위키와 모듈 문서 모두에 리비전·diff·복원을 적용한다. 근거: 초안 §8, 사용자 "위키·문서의 리비전·diff·복원 ... 확정 범위에 반드시 포함". 파일 내부 차이 분석 제외(X-03)는 업로드한 연구 파일에 관한 것이며 문서 diff와 무관하다.
- **D-28 감사로그.** 생성·삭제·이름 변경 등을 기록하는 감사로그를 이번 범위에 포함한다. 대상 이벤트·열람 권한·보존 기간은 D-57. 근거: 사용자 "생성·삭제·이름 변경 등을 기록하는 감사로그를 이번 범위에 포함합니다".
- **D-29 복원 규칙 설계.** 문서 복원과 연결된 업무·수강 진도의 상태 변경을 혼동하지 않도록 복원 규칙을 설계한다. 구체 규칙은 D-58. 근거: 사용자.

### 1.7 체크리스트

- **D-30 체크리스트 공통 입력.** 체크리스트는 에디터가 있는 화면에만 제한하지 않는다. 에디터가 없는 화면: 체크박스와 내용 입력란, 항목 추가·수정·삭제, 완료·미완료 변경. 에디터가 있는 화면: 본문 체크리스트 작성, 별도 체크리스트 입력 영역, 같은 체크리스트를 함께 보여줄 때 양쪽 수정 결과 일치. Markdown 가져오기: 붙여넣은 체크리스트에서 상태와 내용 추출, `- [ ]`는 미완료, `- [x]`는 완료, 일반 체크박스·내용 입력 영역에 채우고 사용자가 확인·수정. 문서와 별도 폼에 같은 내용을 독립적으로 중복 저장하지 않는다. 같은 체크리스트를 다루는 화면은 동일한 항목과 상태를 참조한다. 일반 체크리스트와 실제 업무·강의 진도 연결은 구분하며, 일반 체크 항목이 자동으로 업무를 생성하거나 강의를 완료시키지 않는다. 모든 체크리스트를 문서 본문에만 저장하거나 모두 업무로 만드는 것으로 해석하지 않는다. 근거: 초안 §9, 사용자. '업무로 전환'·'기존 업무·강의 회차 연결'은 제안 단계(P-10). 저장 구조·본문-폼 연결·Markdown 재가져오기 처리는 설계 대상(O-04).

### 1.8 공통 업무·일정

- **D-31 업무·일정.** 업무와 한 단계 하위 업무. 상태·우선순위·담당자·시작일·마감일. 태그·체크리스트·예상 시간. 마일스톤·선행 및 후행 관계. 반복 업무. 회의·발표·행사 일정. 목록·칸반·달력·간트. 검색·필터·정렬·저장한 보기. 일반 업무는 여러 담당자가 있어도 하나의 완료 상태를 공유한다. 강의 이수는 참여자별 상태를 유지한다. 선행 업무의 일정 변경은 영향과 충돌을 보여준 뒤 사용자가 후속 재배치를 승인한다. 미완료 반복 업무는 남겨두고 다음 회차는 원래 일정대로 생성한다. 근거: 초안 §10, 사용자 "일반 업무의 완료는 공유 상태이고 강의 이수는 사용자별 상태".

### 1.9 공통 스톱워치·시간 기록

- **D-32 시간 기록.** 모든 모듈에서 시작·일시정지·재개·종료. 업무·문서·공부·강의 회차·취미 활동에 연결. 측정 후 분류 가능. 수동 입력·수정·수정 이력·메모. 일·주·월 집계. 예상 시간과 실제 시간 비교. 사용자당 모든 워크스페이스를 통틀어 실행 중인 타이머 하나. 앱을 닫아도 측정 지속, 재접속 시 복구. 개인 시간 기록 기본 비공개, 선택한 집계만 공유. 순공부시간은 강의 시청을 제외한 능동적 공부로 정의한다. 실제 인강 수강시간·휴식시간·영상 원본 길이·배속 기준 예상 시간은 서로 구분한다. 근거: 초안 §11, 사용자.

### 1.10 모듈별 기능

- **D-33 프로젝트 모듈.** 생성·수정·복제. 키·이름·설명·아이콘·리더·멤버·그룹. 목표·범위·기간·공개 설정. 업무·하위 업무·체크리스트·담당자·우선순위. 프로젝트별 상태와 업무 설정. 마일스톤·의존 관계·반복 업무. 칸반·달력·간트. 예상·실제 작업 시간. 요구사항·설계·회의록·결정·매뉴얼·인계 문서. 산출물·완료 기준·위험·문제 기록. 회고와 재사용 템플릿. 보관·보관 해제·삭제·복구. 근거: 초안 §12.

### 1.12 이후 추가된 결정

- **D-40 관리자 열람과 문서별 비공개의 관계.** 워크스페이스 관리자는 해당 공간의 비공개 문서도 열람한다. 문서별 비공개 예외(D-20)는 일반 멤버에게 적용된다. 관리자에게도 비공개인 개인 노트(D-22)는 별도 영역·권한으로 처리한다. 근거: 사용자 "O-21은 해소한다. 워크스페이스 관리자는 해당 공간의 비공개 문서도 열람한다". O-21 `[해소]`.
- **D-41 휴지통 보존 기간.** 휴지통 기본 보존 기간은 30일이며 관리자가 설정할 수 있다. 근거: 지침(32개 선택 9번), 사용자 "휴지통 기본 보존 기간 30일과 관리자 설정 가능을 확정 결정에 추가한다". 최초 작성 시 누락되었던 항목이다(7절 변경 이력).
- **D-42 품질 검사 검증 기록 방식.** 개발 지침의 설정은 저장소 초기화 단계에서 구현한다. 설정이 실제로 위반을 잡는지 확인한 기록은 실행 명령·대상 커밋 SHA·결과·필요한 실패 로그를 PR이나 작업 보고에 남기는 것을 기본안으로 한다. 별도 증거 프레임워크를 만들지 않는다. 근거: 사용자 "검증 기록은 실행 명령·대상 SHA·결과·필요한 실패 로그를 PR이나 작업 보고에 남기는 기본안으로 정리한다". O-24 `[해소]`.
- **D-43 열린 항목의 처리 방식.** 열린 항목은 사용자 결정과 기술 설계로 나눈다. 기술 설계는 검토자가 근거·권장안·대안을 제시하고 구현 시 진행하며 무조건 사용자에게 선택을 넘기지 않는다. 기능 축소·권한 확대·새 서비스나 비용 추가는 사용자 결정으로 남긴다. 근거: 사용자.
- **D-45 인증 방식: OIDC 전용.** 인증은 OIDC 전용으로 한다. Keycloak을 기준 제공자로 연동·검증하되 Keycloak 전용 API에 불필요하게 의존하지 않고 표준 OIDC를 사용한다. 사용자 로그인·자격 증명·비밀번호 복구·MFA는 인증 제공자가 담당한다. fvoci는 앱 세션·사용자 프로필·워크스페이스 초대·멤버십·역할·문서 권한을 담당한다. OIDC 로그인 성공만으로 모든 워크스페이스 접근 권한을 부여하지 않는다. 사용자 식별은 이메일이 아니라 발급자(issuer)와 subject의 조합을 기준으로 하며, 같은 이메일이라는 이유로 계정을 자동 병합하지 않는다. 개발·통합 테스트에서는 격리된 Keycloak 환경으로 로그인·세션 만료·로그아웃·권한 거부를 검증한다(D-10의 컨테이너 목록에 추가). 셀프호스트 초기 관리자 지정과 초대 수락 절차는 D-51. Keycloak을 배포에 필수 포함할지 외부 OIDC 서버를 연결할지는 배포 설계에서 구분한다(O-25). 자체 비밀번호 로그인·복구와 SAML은 제외한다(X-09). 근거: 지침(인증 방식 전달 문구) "인증 방식을 OIDC 전용으로 확정한다". O-13 `[해소]`.
- **D-46 저장소 초기 구조 기준.** 2026-10-17 전달받은 디렉터리 구조(`docs/repo-structure.md`)를 fvoci의 초기 구조 기준으로 승인한다. 예시의 빈 폴더와 파일을 모두 미리 만들 필요는 없으며 구현에 필요한 순서대로 만든다. 개발 지침 파일명은 `docs/development.md`로 통일하고 이전 파일과 중복 유지하지 않는다. 이 승인은 구조 기준과 문서 정리에 한정하며 제품 구현 착수 승인은 별도다. 근거: 사용자 "전달한 디렉터리 구조를 fvoci의 초기 구조 기준으로 승인한다". C-02 `[해소]`.
- **D-47 사용자 결정과 구현 선택의 경계.** 사용자 결정이 필요한 것은 기능 범위·권한·삭제 및 보존 정책·비용·외부 서비스 추가처럼 제품에 영향을 주는 사항이다. 파일명·폴더 배치·lint 설정·검증 결과 기록 방식은 승인된 원칙 안에서 검토자가 판단하고 변경 이유만 간단히 기록한다. 명시적으로 확정한 요구와 기술 구현 선택을 구분하되, 모든 구현 선택을 사용자 승인 대기로 만들지 않는다. D-43을 구체화한다. 근거: 사용자.
- **D-48 번호 체계.** 모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유한다. DEV-1, DEV-2를 각각 무엇이 차지하든 중복되지 않는다. 화면에서는 유형 아이콘과 제목을 표시한다. 근거: 사용자 "모듈 인스턴스마다 항목·업무·문서가 번호열 하나를 공유합니다". O-01 `[해소]`. P-03 채택.
- **D-49 개인 노트 공유.** 개인 노트는 기본 비공개이되 소유자가 특정 사람에게 읽기·수정 권한을 줄 수 있다. 공유해도 개인 소유는 유지되고, 상대방의 워크스페이스 관리자에게 권한이 따라가지 않는다. 기존 원본 공유 방식(D-23)과 일치한다. 근거: 사용자. O-02 `[해소]`. P-04 `[기각]`.
- **D-50 시간대 규칙.** 정확한 시각은 UTC 기준으로 저장하고 사용자 시간대로 표시한다. 날짜만 있는 일정은 날짜 그대로 보존한다. 개인 시간 집계는 사용자 시간대, 공동 반복 일정은 일정에 지정한 시간대를 기준으로 한다. 근거: 사용자. O-05 `[해소]`.
- **D-51 계정·초대·인계·삭제·초기 관리자.** OIDC 로그인 후 초대를 수락한다. 초대 대상 확인 없이 링크 소지만으로 가입시키지 않는다. 마지막 소유자는 인계 없이 탈퇴할 수 없고, 소유권 인계는 수신자 수락으로 완료한다. 워크스페이스 삭제는 소유자만 가능하며 확인 후 휴지통으로 보낸다(보존 기간은 D-41). 초기 관리자는 운영자가 지정한 OIDC 식별자로 설정하고 "첫 로그인 사용자 자동 관리자"는 사용하지 않는다(X-10). 근거: 사용자. O-06 `[해소]`.
- **D-52 운영 한도.** 파일 하나의 최대 크기·워크스페이스 총 저장량·업로드 동시성·알림 발송률을 설정 가능하게 한다. 구체적인 기본값은 예상 사용량과 테스트 결과로 검토자가 제안하며(O-26), 코드에 임의의 고정값을 박지 않는다. 근거: 사용자. O-07 `[해소]`.

- **D-60 의존성 라이선스 정책.** 상업 이용·수정·재배포·SaaS 운영에 적합한 허용적 라이선스를 우선한다. MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, PostgreSQL License를 기본 허용 후보로 두되 실제 사용할 버전·구성요소의 조건을 확인한다. 직접·전이 의존성, 복사해 온 코드, WASM·폰트·아이콘도 확인한다. GPL·AGPL·LGPL·MPL 등 카피레프트, SSPL·BUSL·비상업용·사용 목적 제한·상용 계약 필수·라이선스 불명 구성요소는 자동 도입하지 않고 조건과 대안을 보고해 별도 승인받는다. 이중 라이선스는 허용되는 쪽을 선택할 수 있는지 확인하고 근거를 기록한다. 오픈소스 코어와 유료·Enterprise 확장을 구분하며 저장소에 MIT 파일이 있다는 이유로 전체 기능을 MIT로 간주하지 않는다. Docker 분리로 의무가 사라진다고 판단하지 않고 앱 포함 코드·별도 서비스·배포 이미지 OS 패키지를 구분해 검토한다. 저작권 고지·라이선스 원문·NOTICE를 배포물에 보존한다. 설치 버전을 고정하고 의존성 변경 시 라이선스 검사를 수행하며 기존 Cargo·pnpm 도구를 활용하고 새 검사 프레임워크는 만들지 않는다. 현재 선택한 rhwp·Meilisearch·Tiptap과 Office 뷰어 후보도 실제 사용할 패키지·버전·기능 범위로 확인하고, 조건이 충돌하면 조용히 대체하거나 예외 처리하지 않고 보고한다(O-28). fvoci 자체의 공개 라이선스는 별도 결정이다(O-27). 전문은 `docs/development.md` 7절. 근거: 지침(의존성 라이선스 전달 문구).
- **D-61 S3 호환 저장소 대상.** 운영 S3 호환 저장소는 Cloudflare R2를 우선 대상으로 한다. 로컬·CI 테스트 저장소는 SeaweedFS의 고정 버전 이미지를 우선 검토한다(LICENSE 확인: Apache-2.0). 라이선스와 필요한 S3 API 호환성(multipart·완료·중단·재개)을 확인하고, 테스트용 독립 버킷·볼륨으로 격리한다. 자체 S3 서버는 구현하지 않는다. 로컬 검사 성공을 R2 검증 완료로 간주하지 않으며, 실제 R2 연결·자격 증명·비용이 필요한 검증은 별도로 요청받는다. 기존 로컬 파일 저장소 지원은 유지한다. 근거: 사용자. - **D-64 CI 구조 원칙.** CI는 공통 베이스 이미지와 저장소의 표준 명령을 재사용한다. 기존 `deploy/docker/dev.Dockerfile`을 베이스로 쓰고 Rust·Node·pnpm·검사 도구·시스템 의존성을 고정 버전으로 제공한다. 베이스 이미지는 Dockerfile·도구 버전·시스템 의존성이 바뀔 때와 보안 업데이트 주기에만 갱신하고 제품 커밋마다 만들지 않는다. 후속 job은 같은 이미지 digest를 쓰고 latest에 의존하지 않는다. CI YAML은 트리거·권한·job 의존·공통 명령 호출·결과 업로드만 담당하며 설치·판정 로직을 긴 셸 블록으로 쓰지 않는다. 로컬과 CI는 같은 xtask·pnpm 명령을 쓴다. 베이스 이미지에 제품 소스·시크릿·실행 중 DB를 넣지 않고 PostgreSQL·Meilisearch·테스트 저장소는 별도 컨테이너로 격리한다. 제품 바이너리·웹 빌드는 공유 가능하면 한 번 만들어 소스 SHA·아키텍처·빌드 옵션이 맞는 것만 소비한다. 의존성 캐시는 속도용이며 없어도 빌드·검증이 된다. 현재 규모에서는 단순한 job으로 시작하고 병목 측정 전 샤딩·matrix·범용 실행 프레임워크를 만들지 않는다. 이미지 배포 승인 전에는 로컬 빌드까지만 준비한다. 근거: 지침(CI 구조 전달 문구). 구현은 `.github/workflows/{base-image,ci}.yml`, 설명은 `docs/development.md` 10절.
- **D-65 저장소·CI 이미지 공개.** 저장소는 https://github.com/fvoci/GroundZero 이며 기존 AISFlow/fvoci·fvoci/FVOCI와 혼동하지 않는다. GroundZero는 공개 저장소로 운영하고 CI 베이스 이미지는 GHCR 공개 패키지 `ghcr.io/fvoci/groundzero-ci-base`에 게시한다. 저장소·CI 이미지 공개와 제품 정식 릴리스·SaaS 공개 배포는 구분한다. - **D-66 프론트엔드 UI 구성.** 기본 UI는 shadcn-svelte(기반 Bits UI)를 쓰고 스타일은 Tailwind CSS와 공통 디자인 토큰으로 관리한다. 문서 편집기는 Tiptap(D-27). Skeleton 등 다른 종합 UI 시스템을 병행 도입하지 않는다. 업무 달력·간트·칸반 드래그는 별개로 필요 시 기존 구현을 조사하며, 날짜 선택 컴포넌트를 업무 달력 구현으로 보지 않는다. 도입: 현재 Svelte·Vite·TypeScript 구성과 호환되는 공식 방식(Vite 수동 설치)으로, SvelteKit·SSR로 전환하지 않는다. 최초 도입은 현재 화면에 필요한 구성요소(버튼·입력란·체크박스·라벨·대화상자·메뉴·사이드바)로 제한한다. 공통 UI는 `apps/web/src/lib/ui`에 모으고 기능별 코드에서 복사하지 않는다. CLI 기본 경로 대신 별칭(`$lib/ui`)으로 기존 구조에 맞춘다. 재사용·수정: 기본 동작·접근성·키보드 처리는 제공 구현을 우선 쓰고, 디자인 수정은 색·글자·간격·모서리·포커스 토큰 중심으로 한다. 실제 요구 없는 커스텀 래퍼·범용 폼 엔진·자체 모달·메뉴·포커스 관리자를 만들지 않는다. 가져온 컴포넌트의 출처·버전·명령을 `apps/web/src/lib/ui/README.md`에 기록하고 수정분을 최소화한다. 라이브러리 사용이 접근성 검증을 대신하지 않는다. 가독성: 글자 크기는 rem 기반, 브라우저 기본 크기와 확대 설정 존중, CJK 본문·입력란·목록의 공통 타이포그래피와 줄 높이 토큰, 키보드 이동·보이는 포커스·라벨·오류 안내·대화상자 종료 후 포커스 복귀 확인, 색상 배지 외 이름·아이콘 병행. 일반 체크리스트는 에디터 없는 화면에서도 체크박스와 입력란으로 쓰고 문서 편집기와 같은 데이터·권한 규칙을 따른다(D-30). 범위: 공통 UI 기반 선택과 최소 도입이며 전체 화면 개편·새 기능 추가가 아니다. 근거: 지침(프론트엔드 UI 전달 문구). 도입 기록은 `docs/development.md` 11절.
- **D-67 개발 도구 사용 원칙.** 저장소 검색은 rg, 파일 목록은 `rg --files`를 우선 쓰고 경로·유형을 좁힌다. rg는 숨김·ignore 파일을 제외하므로 결과가 없다는 것만으로 파일이나 호출자가 없다고 단정하지 않으며 필요할 때만 `--hidden`·`--no-ignore`를 쓴다. - **D-77 ETag·조건부 요청·캐시 범위(CDN 앞에서도 같은 동작).** CDN이 없는 셀프호스트와 Cloudflare·CloudFront 뒤에서 권한과 저장 정합성이 같게 유지되도록 앱이 캐시 정책을 정하고 CDN 설정은 예시로 둔다. (1) 문서 단건 조회(`GET /api/documents/{id}`, 위키·모듈 문서·개인 노트)는 강한 ETag를 준다. 값은 실제 응답 바이트(제목·본문·사용자별 필드·직렬화 형식)와 요청한 사용자로 만든 해시이고, `If-None-Match`(약한 비교)는 매 요청 세션·권한을 확인한 뒤에만 비교해 같으면 304다. 권한이 철회되면 404, 로그아웃이면 401이므로 이전 ETag로 304를 받지 못한다. (2) 문서 저장(`PUT`)은 선택적으로 `If-Match`를 받는다. 문서 행을 잠근 뒤 같은 요청 재시도(`request_id`) 판단 다음, 기존 `base_revision` 비교 앞에서 같은 행으로 지금 표현의 ETag를 만들어 강한 비교를 하고, 다르면 412와 서버 최신본(409와 같은 모양, 초안은 클라이언트가 보존)을 준다. 약한 ETag는 `If-Match`에서 맞지 않는다(RFC 9110). 조건 확인과 갱신은 같은 트랜잭션·같은 행 잠금 안이다. `If-Match`가 없으면 `base_revision`(409)만으로 지금처럼 동작하고, 실시간 편집의 CRDT 갱신·저장 확인·멱등 키는 역할을 바꾸지 않는다. (3) 편집 API는 압축·변환하지 않는다: 앱은 API 응답을 압축하지 않고 `Cache-Control`에 `no-transform`을 붙여 중간 장치가 압축하며 ETag를 약하게 바꾸지 않게 한다(Cloudflare는 no-transform이면 압축하지 않음). 클라이언트는 강한 ETag일 때만 `If-Match`를 보내고, 약하게 바뀌었으면 `base_revision`만 쓴다. (4) 캐시 범위: 해시 파일명 정적 자원(`/assets/*`, `/rhwp/<입력 해시>/*`)은 `public, max-age=31536000, immutable`; HTML 진입점·SPA 경로·해시 없는 정적 파일·`/rhwp/manifest.json`은 `no-cache`(재검증); `/api`·`/auth`·`/healthz`는 문서 단건 조회만 `private, no-cache, no-transform`이고 나머지(인증·세션·개인 데이터·권한 첨부·내보내기·익명 공유 링크 포함)는 모두 `no-store`. 없는 해시 자원은 SPA 화면이 아니라 404. 압축 사본을 고르는 정적 응답은 `Vary: Accept-Encoding`. (5) CDN 예시(`deploy/cdn/`): Cloudflare는 민감 경로 Cache Bypass 규칙을 다른 캐시 규칙보다 뒤에 두어 Cache Everything 등이 덮지 않게 하고, API 경로는 Respect Strong ETags 켬·브라우저 TTL은 원본 존중, 정적 해시 경로만 캐시·압축. CloudFront는 민감 경로를 CachingDisabled + AllViewer(쿠키·Authorization·Origin·조건부 요청 헤더 전달)로, 해시 자원만 CachingOptimized로. 사용자 정보를 캐시 키에 넣는 것으로 격리를 대신하지 않는다. 로그인·로그아웃·OIDC 콜백·쓰기 요청의 메서드·Set-Cookie·If-Match·304·412와 실시간 웹소켓은 그대로 원본에 전달·비캐시. (6) 객체 저장소(R2·S3)의 객체 ETag, API ETag, 무결성 체크섬(SHA-256)은 서로 다른 값이고 섞지 않는다. 비공개 첨부는 앱을 거쳐 내려주며 영구 공개 URL로 바꾸지 않는다. 업로드 조각(5~64 MiB)은 요청마다 프록시 한도 안이고 완료 단계는 전체 파일을 다시 보내지 않는다. 새 캐시 서버·범용 프레임워크는 더하지 않고, 실제 클라우드 계정 설정·유료 서비스 생성은 별도 승인 대상이다. 실제 CDN 검증은 승인된 대상이 생길 때까지 NOT RUN. 근거: 사용자 "ETag·조건부 요청·CDN 캐시 정책을 docs/decisions.md에 기록하고, Cloudflare 또는 CloudFront 앞에서도 권한과 저장 정합성이 유지되도록 구현한다. CDN 없는 셀프호스트도 동일하게 동작해야 한다."

(1) 공통 정본 하나: 업무(`tasks`, 상태는 공유), 문서(`documents`, 한 엔진·리비전), 체크리스트(업무는 `checklist_items`, 문서는 본문 노드), 첨부·버전(`files`·`file_versions`), 시간 기록(`time_entries`, 종류 일·공부·강의·휴식·기타), 일정(`events`), 권한(`app_item_access`·`app_task_access`·`app_document_access`), 알림, 감사 기록을 모든 모듈이 같이 쓰고 모듈별 사본을 두지 않는다. 칸반·목록·달력·간트는 같은 업무 목록을 보는 방식이며 한 보기의 변경은 다시 읽은 같은 목록으로 다른 보기에 보인다. (2) 모듈 전용 정본은 강의의 강좌·회차·개인 진도, 스터디의 계획 단위·개인 진행, 항목 기록(연구 문헌·데이터·변수·분석·투고, 프로젝트 산출물·위험·문제·회고, 스터디 자료·모임·시험·복습, 취미 재료·장비·장비 사용·활동·결과물)뿐이다. (3) 완료 조건: 업무 완료는 담당자 모두에게 하나(D-31), 강의 이수·스터디 진행은 사람마다(진행 행은 본인만 읽고 함께 보기는 집계만), 재수강은 시간 기록에 더하고 완료 회차 수는 늘리지 않는다(D-37). (4) 모듈별 흐름: 모듈(키·이름·아이콘) → 항목(제목·설명·정보·리더·멤버·공개 범위) → 항목 화면의 업무·문서·일정·첨부·기록과 모듈 전용 패널(강좌·스터디 계획) → 보관·휴지통·복구. (5) 대조에서 나온 보완: 칸반 끌어서 놓기(D-79), 달력 범위와 집계 연결(D-80), 항목별 시간 합계(같은 시간 기록에서 항목 아래 업무·회차·스터디 단위·항목 대상 기록을 모아 종류별로, 개인 기록은 본인 것만, 공유 집계는 D-32 공유를 켠 사람만), 표시 언어와 날짜·시간 정책(D-81). 기존 결정에 없던 세부는 사용자 선택으로 더한다: 모듈 설명(관리자), 모듈 휴지통·복구(모듈 행만 휴지통에 들고 되살리면 모듈만 돌아온다. 그 전에 따로 지운 항목은 자기 묶음에 남고 항목의 공개 범위·멤버는 바꾸지 않아 권한이 넓어지지 않는다. 관리자만 되살린다), 시간 기록 종류 "취미". 근거: 사용자 "모듈별 기능을 현재 구현과 대조하고, 빠진 기능과 보완 사항을 docs/decisions.md에 기록한 뒤 구현을 이어간다. 기존 결정과 구현을 재사용하고, 새로운 기획을 무제한으로 늘리지 않는다."
- **D-79 칸반 끌어서 놓기.** 화살표 단추와 Alt+방향키 이동을 그대로 두고 마우스 끌어서 놓기와 터치 이동을 더한다. 열 사이 이동(상태)과 열 안 순서는 기존 이동 API(`PUT /api/tasks/{id}/position`) 하나로 저장한다. 마우스는 카드에서 일정 거리(6px) 이상 움직일 때만 끌기로 보아 누르면 카드가 열리고, 터치·펜은 손잡이에서만 끌어 카드 위를 쓸면 화면이 스크롤된다. 화면에 먼저 반영하고 저장이 실패하면 되돌리며, 동시 변경(400)·권한 철회(403)·삭제(404)·보관(409)·네트워크 실패를 알린 뒤 최신 목록과 항목을 다시 읽는다. 기본 순서가 아닌 정렬에서는 열만 바꾼다. 사용자 정의 열·자동화 규칙은 넣지 않는다. 근거: 사용자 "현재 화살표 버튼과 Alt+방향키 이동을 유지하면서 마우스 드래그앤드롭과 터치 이동을 지원한다 … 사용자 정의 열·자동화 규칙은 이번에 임의로 추가하지 않는다."
- **D-80 달력 범위와 날짜 출처.** 달력은 하나의 조회(`GET /api/workspaces/{id}/calendar`)를 워크스페이스 전체 → 모듈 → 개별 항목의 범위로 보는 방식이다. 워크스페이스 달력에는 모듈·항목 거르기를 두고, 모듈 화면에는 그 모듈로, 항목 화면에는 그 항목으로 범위를 정한 같은 달력을 연결한다. 모듈별 일정 사본은 만들지 않는다. 날짜 출처는 기존 정본을 그대로 읽는다: 일정(반복 회차 포함), 업무(시작일·마감일, 앞으로 생길 반복 업무), 강의 회차 수강 예정일, 스터디 계획 단위 계획일, 연구 투고 기록의 제출 예정일·수정 마감일, 프로젝트 산출물 마감일, 취미 연습 일정(항목 일정). 강의·스터디는 보는 사람의 개인 계획일이 있으면 그것을, 없으면 공통 계획일을 쓰고 어느 쪽인지 표시한다. 개인 계획일은 본인 것만 읽는다(진도 행은 본인만, D-37·D-36). 모든 출처는 보는 사람이 그 항목을 볼 수 있을 때만 나온다(`app_item_access`). 개인 시간 기록은 달력에 넣지 않는다(D-32 기본 비공개). 근거: 사용자 "달력의 조회 범위를 워크스페이스 전체 → 모듈 → 개별 항목으로 제공한다. 기존 달력과 일정 데이터를 재사용하고, 모듈별 별도 일정 사본을 만들지 않는다."
- **D-81 표시 언어와 날짜·시간 정책.** (1) 언어: 처음 지원 언어는 한국어(원본)와 영어. 메뉴·폼·오류·알림·달력·접근성 라벨·내보내기 화면을 번역하고, 사용자가 쓴 문서·제목·모듈 이름·파일 이름은 번역하지 않는다. 도구는 Paraglide JS 2(MIT, 사용자 선택)이고 메시지는 `apps/web/messages/{ko,en}.json` 하나씩이다. 문자열을 이어 붙이지 않고 변수 치환·복수형을 쓰며, 두 언어의 키 누락·불일치는 `cargo xtask check`가 거부한다. 서버의 오류 코드·감사 이벤트·상태 값은 언어 중립 값으로 두고 화면이 번역하며, 번역 문자열을 DB 상태 값으로 쓰지 않는다. (2) 사용자 설정: 표시 언어, IANA 시간대, 한 주 시작(월·일), 시각 표시(12·24시간)를 따로 고른다. 저장한 값이 우선이고 계정에 보존해 기기 사이에 같다. 저장한 값이 없으면 처음에 브라우저 언어·시간대를 제안하고 주 시작·시각 형식은 고른 언어의 로케일 관례로 정한다. 브라우저가 바뀌어도 저장한 값을 덮어쓰지 않는다. 설정은 표시만 바꾸고 저장된 일정 시각·날짜를 바꾸지 않는다. (3) 시간 데이터(D-50 유지): 실제 시점은 UTC로 저장·전송하고 사용자 시간대로 보인다. 날짜만 있는 마감·수강일·종일 일정은 날짜로 둔다. 반복 일정은 일정 자체의 시간대와 현지 시각을 보존하고 보는 사람의 시간대와 상관없이 같은 규칙으로 회차를 만든다. DST(사용자 선택): 반복 회차를 만들 때 그 시간대에 없는 현지 시각(봄의 건너뛴 시각)의 회차는 만들지 않고 건너뛴 회차로 표시하며, 두 번 나타나는 시각(가을의 겹친 시각)은 앞선 시각에 한 번만 만든다(RFC 5545 §3.3.10, 반복 규칙은 존재하지 않는 시각을 무시). 반복이 아닌 단건 시각 입력은 RFC 5545 §3.3.5의 개별 DATE-TIME 해석과 구분해, 없는 현지 시각은 저장하지 않고 다른 시각을 고르게 안내하며(조용히 옮기지 않음) 겹친 시각은 앞선 시각으로 해석한다. (4) 시간 기록 집계(사용자 선택): 기록 원본은 나누지 않고, 일·주·월 합계만 보는 사람 시간대의 자정 경계로 나눈다. 일시정지 시각은 저장하지 않으므로 일시정지 시간은 경과 비율로 나눠 뺀다. 나눈 합은 원래 기록의 합과 같다. 주 합계는 사용자의 한 주 시작을 따른다. 스톱워치 경과 시간은 언어·시간대·주 시작과 상관없다. (5) 모든 날짜 화면(워크스페이스·모듈·항목 달력, 날짜 선택, 간트, 홈의 오늘, 강의·스터디 계획, 시간 기록·집계)이 같은 설정을 쓰고 '오늘'·주 범위·월 경계를 사용자 시간대로 계산한다. 일요일 고정 배열이나 서버 지역 시간에 기대지 않는다. 공동 일정은 원래 일정 시간대가 보는 사람과 다를 때 그것도 보인다. 날짜·숫자·시각 서식은 `Intl` 위의 작은 공통 포매터 하나를 쓴다. 근거: 사용자 "i18n과 날짜·시간 표시 정책을 docs/decisions.md에 기록하고, 진행 중인 달력 작업과 함께 구현한다."
- **D-82 사용자 피드백 규칙.** 일반 완료는 화면 오른쪽 아래 토스트(모바일은 아래쪽 탐색·키보드와 겹치지 않는 자리), 입력 오류는 해당 필드 옆, 저장 실패·충돌은 그 화면에 남는 메시지(입력 보존, 다시 시도 동작), 연결 상태는 배너, 멘션·초대는 알림함으로 나눈다. 자동 저장 성공은 편집기의 상태 표시로만 알린다. 같은 오류가 반복해도 토스트를 쌓지 않고 하나를 갱신한다. 토스트·배너는 화면 낭독기에 알리고(`aria-live`) 키보드로 닿고 닫을 수 있다. 기존 UI 구성요소를 먼저 쓰고 모든 문구는 i18n(D-81)에 연결한다. 근거: 사용자 "사용자 피드백 규칙을 decisions에 추가한다."
- **D-83 운영 로그 레벨과 JSON Lines.** 기존 `tracing`을 확장하고 새 로그 프레임워크·서비스를 두지 않는다. (1) 레벨: 운영 기본 INFO. `FVOCI_LOG`(없으면 `RUST_LOG`)로 ERROR~TRACE와 모듈별 거르기(예: `info,fvoci_server::collab=debug`). 시작할 때 한 번 읽으므로 바꾸면 다시 시작하고, 잘못 쓰면 시작하지 않는다. ERROR는 처리 실패·정합성 문제, WARN은 복구 가능한 이상(바깥 서비스 실패 502 포함), INFO는 시작·종료·주요 작업 결과와 요청마다 접근 줄 하나(거절이면 `error_code`), DEBUG·TRACE는 진단. 입력 오류·권한 거부·충돌(4xx)은 오류 줄을 남기지 않고 접근 줄의 `status_code`로 본다. `/healthz`와 정적 파일 접근 줄은 DEBUG. (2) 형식: stdout에 한 줄에 JSON 객체 하나(`FVOCI_LOG_FORMAT=json`, 기본). 공통 필드 `timestamp`(UTC RFC 3339)·`level`·`target`·`event`(안정된 기계용 코드)·`message`, 해당하면 `request_id`·`job`·`job_id`·`status_code`·`duration_ms`(밀리초 숫자)·`error_code`(응답 오류 코드와 같은 값)·`detail`. 색·여러 줄 없음(줄바꿈은 JSON 이스케이프). 로그 문구는 UI 언어와 상관없다. 개발용 `pretty`는 같은 사건·필드를 한 줄 글로 쓴다. (3) 추적: 요청마다 id(앞단의 안전한 `x-request-id` 또는 새 UUIDv7, 받은 값은 추적용일 뿐 권한과 상관없다)를 응답 머리글·오류 본문(`request_id`)·로그 줄에 같게 넣는다. 주기 작업은 실행마다 작업 id. 화면은 서버 오류(5xx)에 안전한 문구와 요청 ID만 보인다. 서버 쪽 실패는 응답으로 바꾸는 곳에서 한 번만 남긴다. (4) 민감정보: 어느 레벨에서도 비밀번호·토큰·쿠키·Authorization·OIDC 코드·서명 URL·문서 본문·첨부 내용, 요청·응답 본문·머리글·쿼리, 설정 값, DB 바인딩, 바깥 서비스 오류 원문을 쓰지 않는다. 접근 줄은 실제 경로가 아니라 경로 틀(`/api/public/{token}`)을 쓴다. 오류는 우리가 붙인 분류·SQLSTATE·제약 이름만 남긴다. HTTP·TLS·웹소켓·OIDC·DB 라이브러리는 거르기와 상관없이 `info`까지만 내보내고, 경고·오류에 파일 내용을 찍는 PDF 뽑기 라이브러리(`pdf_extract`·`lopdf`)는 내보내지 않는다. sqlx의 SQL 문장 로그(느린 쿼리 포함)는 끄고, 주기 작업 함수의 경고에는 오류 원문 대신 SQLSTATE만 쓴다(마이그레이션 0056). 패닉은 위치만 담은 한 줄로 남긴다(패닉 값은 쓰지 않는다). (5) 감사 기록은 DB(`audit_log`)에 따로 남아 로그 레벨과 상관없다. 로그 보관은 Docker `json-file` 회전(서비스마다 기본 10 MB × 5, `FVOCI_LOG_MAX_SIZE`·`FVOCI_LOG_MAX_FILE`)에 맡기고 앱 안 파일 로그·회전기, 로그 서버, 실시간 로그 UI, 외부 전송은 두지 않는다(범위 밖). 조회·일시 상세 로그·원복 절차는 `docs/self-hosting.md` 8절. 근거: 사용자 "운영 로그 레벨과 JSON Lines 출력 정책을 적용한다."
- **D-84 Paraglide 빌드 도구의 라이선스 예외(빌드 시점 한정).** 허용 목록(D-60·D-68)은 그대로 두고 아래 패키지·판에만 예외를 둔다. SPDX `Apache-2.0 WITH LLVM-exception`. 대상: `@bytecodealliance/jco-transpile` 0.13.0, `@bytecodealliance/jco-node-fs` 0.3.2(그 플랫폼 판 `-darwin-arm64`·`-linux-x64-gnu`·`-linux-arm64-gnu` 0.3.2 포함), `@bytecodealliance/preview2-shim` 0.24.1·0.25.0, `@bytecodealliance/preview3-shim` 0.6.1. 의존 경로: `@fvoci/web`(개발 의존성) → `@inlang/paraglide-js` 2.29.0·`@inlang/plugin-message-format` 4.5.4 → `@inlang/sdk` 4.0.4 → `@lix-js/sdk` 0.20.1 → `@bytecodealliance/jco-transpile` 0.13.0 → 나머지. 메시지 컴파일(빌드) 때만 쓰고 제품 이미지·웹 번들에는 들어가지 않는다(제품 이미지의 `/srv/fvoci/web`에서 해당 코드 0건, 2026-10-18 확인). 조건: 판이 바뀌면 다시 검토하고, 제품 번들에 들어가면 이 예외로 허용하지 않는다. `xtask/src/licenses.rs`의 패키지·판 예외와 같다. 근거: 사용자 "Approve, build-time only"(2026-10-17).
- **D-85 컨테이너 이미지는 Debian 기반·digest 고정.** 제품 이미지 단계(`rust:*-bookworm`, `node:24.22.0-bookworm-slim`, `debian:bookworm-slim`)와 PostgreSQL(`postgres:18.3-bookworm`, 이전 `-alpine`)은 Debian 12(bookworm) 기반을 쓴다. 공식 Debian 판이 없는 Meilisearch·SeaweedFS(Alpine)와 Keycloak(Red Hat UBI)은 공식 이미지를 그대로 쓴다. 모든 제3자 이미지(Compose 개발·테스트·셀프호스트, CI 서비스, Dockerfile의 `FROM`)는 판 태그와 여러 아키텍처 index digest(`이름:태그@sha256:…`)로 고정한다. PostgreSQL을 Alpine에서 Debian으로 바꾸면 데이터 파일 소유자(uid 70 → 999)와 정렬 라이브러리(musl → glibc)가 달라지므로 기존 데이터 볼륨은 그대로 올리지 않고 백업 → 새 설치 → 복구로 옮긴다(`docs/self-hosting.md` 6절). 근거: 사용자 "데비안 기반으로 사용해"(2026-10-18), 목표의 "이미지 버전·digest를 고정".
- **D-86 서체는 제품에 넣은 Noto Sans KR·Noto Serif KR·D2Coding(OFL-1.1 예외, 여섯 파일 한정).** 사용자 승인(2026-10-18, O-37): Noto Sans KR 2.004·Noto Serif KR 2.003·D2Coding 1.4.0의 Regular·Bold 여섯 파일에 한해 라이선스와 저작권 고지를 보존해 제품에 넣는다. 다른 패키지나 OFL-1.1 전체를 허용하는 것이 아니다. 외부 CDN과 글자별 조각 요청은 금지한다.
  - 파일은 받은 그대로 `apps/web/src/assets/fonts`에 둔다(부분집합·형식 변환 없음). `cargo xtask notices`가 그 폴더에 정확히 이 여섯 파일과 라이선스 파일 둘만 있고(숨김 파일 제외) SHA-256이 O-37 기록과 같은지, 실제 웹 번들의 서체가 이 여섯뿐인지 확인하며, 서체별 출처·판·SHA-256·저작권·상표 문구와 라이선스 전문을 `THIRD_PARTY_NOTICES.txt`에 싣는다.
  - 불러오기: 미리 받지 않고 `font-display: swap`(받는 동안 시스템 서체). 본문·UI는 Noto Sans KR(첫 화면에서 Regular·Bold 두 파일). D2Coding은 코드·원문(문서 코드, Markdown·LaTeX·CSV 입력, 리비전 비교, `font-code`)이 있는 화면에서만 받고, 번호·단축키 같은 짧은 UI 고정폭 표시는 시스템 고정폭이다(모든 화면이 D2Coding을 받지 않게). Noto Serif KR은 표시 설정의 "문서 본문 서체: 명조"를 고른 브라우저에서 문서를 열 때만 받는다(이 브라우저에만 저장하는 보기 설정, 계정·API·문서 형식은 바꾸지 않음).
  - 전송: 이미지 빌드가 해시 자원(서체·번들)에 br·gzip 사본을 만들고 서버가 `/assets`에서 그대로 보낸다(`/rhwp`와 같은 방식, 원본 파일은 그대로). Noto Sans KR Regular 4.6 MB → br 3.2 MB.
  - 글자 범위(cmap): 세 서체 모두 한글 11,172자. Noto KR 둘은 한자 8,138자·히라가나 93·가타카나 96, D2Coding은 한자 4,620자. 일본어 신자체 일부(辺·変·読 등)는 KR 배포본에 없어 그 글자만 뒤의 시스템 일본어 서체로 그린다.
- **D-87 제품 이미지 릴리스와 버전 표시.** 사용자 지시(2026-10-20): 릴리스 태그의 제품 이미지를 GitHub Actions에서 빌드해 GHCR `ghcr.io/fvoci/groundzero:X.Y.Z`에 게시한다(검사 도구 이미지 `groundzero-ci-base`와 구분, `latest` 없음). D-65가 뺀 "제품 릴리스" 가운데 이 이미지 게시만 허용한다. SaaS 배포·main 병합·태그 생성·이동은 여전히 별도 승인이다.
  - 기준은 검증한 Git 태그(`vX.Y.Z`, 원격에 있고 main에 들어간 커밋)다. 제품 버전은 `X.Y.Z`, 소스 식별자는 그 태그 커밋의 전체 SHA이며, CI가 한 번 정해 빌드 인자·OCI 라벨·확인 기대값에 같이 쓴다. Cargo 패키지 버전(`0.1.0`)은 제품 버전이 아니다.
  - 서버가 컴파일할 때 받아(`build_info`) `/healthz`의 `build`(제품 버전·소스 SHA만), 시작 로그 `server.starting`, `fvoci-server version`에 같은 값을 낸다. 화면은 이 응답을 읽어 계정 메뉴에 보인다. 값 없이 빌드하면 `dev`로 보이며 정식 릴리스로 보이지 않는다. 하나만 있거나 형식이 틀리면 컴파일이 멈춘다.
  - 이 지원 전에 만든 `v0.0.1`은 태그를 옮기지 않고 그대로 빌드한다: 이미지 라벨만 0.0.1·소스 SHA를 가리키고 앱 안에는 버전이 없다. 그 밖의 주입 이전 태그는 거부한다.
  - amd64·arm64는 무료 GitHub-hosted 네이티브 러너(`ubuntu-24.04`, `ubuntu-24.04-arm`, 공개 저장소)에서 한 번씩 빌드하고 둘 다 확인을 통과해야 태그를 붙인다. 같은 태그가 이미 있으면 소스 SHA가 같을 때만 그대로 두고 다르면 실패한다. 게시 권한은 게시 job에만, 기존 `GITHUB_TOKEN`만 쓰고 PR에서는 게시하지 않는다. 사용법은 `docs/development.md` 10절.
- **D-88 셀프호스트 Supabase를 추가 DB 배포 대상으로.** 사용자 지시(2026-10-20): 기존 자체 PostgreSQL 지원과 기본 설정을 유지하면서, 셀프호스트 Supabase의 PostgreSQL을 DB로만 쓸 수 있게 한다. Rust 백엔드·Keycloak/OIDC·S3/R2/local 저장소·Meilisearch·작업 대기열은 그대로이고, Supabase Auth·Storage·Realtime·Data API 연동과 화면의 직접 DB 접근은 들이지 않는다. Supabase Cloud와 서비스 전체 이전은 범위 밖이다.
  - 관리자 연결은 superuser가 아니어도 된다(셀프호스트 Supabase의 `postgres`는 `CREATEROLE`·`CREATEDB`·`BYPASSRLS`만 있다). `db bootstrap`은 이미 있는 역할의 속성을 다시 쓰지 않고 비밀번호만 갱신한 뒤 권한 속성(`SUPERUSER`·`CREATEROLE`·`BYPASSRLS`, 앱 역할은 `CREATEDB`까지)이 없는지 확인해 있으면 멈춘다. 스키마 소유자 지정과 복구처럼 표 소유자로 해야 하는 일은 그동안만 상속 없는 SET 멤버십을 받아 하고 거둔다. 복구에서 관리자 권한은 트리거를 잠시 끄는 설정(`session_replication_role`)에만 쓴다. 전제: 관리자가 두 역할을 만들었거나 그 역할에 ADMIN OPTION이 있어야 하고(아니면 bootstrap이 무엇을 할지 알리고 멈춘다), 복구하는 관리자는 `session_replication_role`을 바꿀 수 있어야 한다(superuser, 셀프호스트 Supabase의 `postgres`는 supautils가 허락, 그 밖의 PostgreSQL은 superuser가 `GRANT SET ON PARAMETER session_replication_role`).
  - 역할 분리(`fvoci_migrator` 소유, 앱은 `fvoci_app` `NOBYPASSRLS`)와 `app.user_id` 트랜잭션 설정 기반 RLS는 그대로다. Supabase `auth.uid()` 정책으로 바꾸지 않고, `fvoci` 스키마를 Data API 노출 스키마에 넣지 않으며 `anon`·`authenticated` 등에 권한을 주지 않는다.
- **D-44 보류 항목의 취급.** 운영자 대상 암호화(H-01)와 외부 플랫폼 자동 시청 추적(H-02)은 현재 필수 범위의 차단 항목이 아니다. 새 승인이 없는 상태에서 구현 범위를 확대하지 않는다. 근거: 사용자 "현재 필수 범위의 차단 항목에서 분리한다. 새 승인이 없는 상태에서 구현 범위를 확대하지 않는다".

## 2. 미승인 제안 (검토자)

사용자가 승인하지 않았다. 결정이 아니며, 채택하려면 사용자가 명시해야 한다.

- **P-01** 데이터 모델을 "공통 코어(항목·문서·업무·체크리스트·시간 기록·권한·참조) + 모듈별 메타데이터와 보기"로 명시하고, 다섯 유형 항목을 공통 테이블 + 유형별 확장으로 둔다.
- **P-02** 모듈마다 "없으면 못 쓰는 최소 사용자 흐름" 하나를 정의해 단계적 검증의 기준으로 삼는다.
- **P-03** `[채택 → D-48]` 번호 단위에 대해 모듈당 하나의 번호열을 항목·업무·문서가 공유하는 방식을 권장. 대안: 유형별 접두어(`DEV-1`, `DEV-T1`, `DEV-D1`), 또는 항목만 번호를 갖고 업무·문서는 하위 경로.
- **P-04** `[기각 → D-49]` 개인 노트는 완전 비공개로 고정하고 협업이 필요하면 워크스페이스로 이동·복제한다. 사용자 명시: "'개인 노트 공유 금지'는 아직 승인되지 않은 제안".
- **P-05** 시간 기록·실행 중 타이머·즐겨찾기·최근 항목을 개인 노트와 같은 사용자 소유 영역에 둔다.
- **P-06** 연구 자료의 "자료 + 버전" 모델을 연구 전용이 아니라 공통 첨부 모델로 올려 프로젝트 산출물·취미 결과물·강의 자료에도 적용한다.
- **P-07** 분석 기록의 연결 대상으로 내부 자료 버전 외에 외부 참조(URL + 커밋 해시나 버전 문자열)를 허용한다.
- **P-08** 자료 버전마다 체크섬을 저장해 무결성 확인과 동일 파일 재업로드 감지에 쓴다.
- **P-09** `[채택·확장 → D-56]` 분석 기록이 참조 중인 자료 버전은 삭제를 막거나 휴지통만 허용한다.
- **P-10** 체크리스트 항목의 '업무로 전환'과 '기존 업무·강의 회차 연결'. 초안 §9의 추가 설계안 포함: 연결 시 실제 업무·수강 기록을 상태의 기준으로 사용, 대상의 수정 권한을 서버에서 확인, 실패하면 잘못된 완료 표시를 남기지 않음, 강의 체크는 해당 사용자의 개인 진도에만 반영. 사용자 명시: "아직 제안 단계로 구분".
- **P-11** `[대체 → D-53]` CRDT OFF 워크스페이스의 충돌 처리를 3-way merge UI가 아니라 낙관적 잠금 + 마지막 저장 경고 + 복사본 저장 수준으로 둔다.
- **P-12** Markdown 원본 편집은 지원 블록이 제한된 보조 모드라고 명시한다. 표·수식·멘션·체크리스트 참조는 왕복 시 손실 가능.
- **P-13** CRDT 상태를 텍스트·JSON으로 투영하는 레이어(리비전·diff·검색 색인·멘션 추출용)를 설계 항목으로 명시한다.
- **P-14** 검색 권한은 인덱스 필터에만 의존하지 않고 결과를 서버에서 재검증한다.
- **P-15** 모듈 보관·삭제 시 참조 키를 별칭으로 남겨 재사용을 막는다.
- **P-16** 테이블마다 RLS 범위가 워크스페이스 소유인지 사용자 소유인지 처음부터 표시한다.
- **P-17** "진도 상태는 항상 사용자별, 업무 상태는 항상 공유"를 일반 규칙으로 올려 스터디 개인·공동 계획에도 적용한다.
- **P-18** 스톱워치는 서버 타임스탬프 기준이며 오프라인 시작은 지원하지 않는다고 명시한다.
- **P-19** 개인 노트 비공개가 앱 권한 수준이며 서버 운영자로부터의 비밀을 보장하지 않는다는 문구를 제품 문서에 넣는다.
- **P-20** 클라이언트 생성 멱등 키 방식을 업로드 완료·업무 생성·스톱워치 시작 전부에 공통 적용하는 구현 원칙으로 올린다.
- **P-21** 강의 회차 상태와 시청 기록을 분리된 엔티티로 둔다(재수강 규칙 구현용).
- **P-22** 홈 Up Next를 위해 각 모듈이 "오늘 할 일" 공통 인터페이스를 제공한다.
- **P-23** `[채택 → O-19 해소]` 백그라운드 작업(색인·미리보기 변환·업로드 정리·반복 업무 생성·알림)을 단일 바이너리 내 워커로 둘지 별도 워커로 둘지 결정 항목으로 올린다(O-19).

기각·철회된 제안

- **P-R01 `[기각]`** 워크스페이스 간 공유·이동을 1차 범위에서 제외하고 참조만 허용. 사용자가 포함을 확정(D-24).

### 3.2 기술 설계

확정된 정책을 구현하는 선택. 검토자가 근거·권장안·대안을 제시하고 구현 시 권장안으로 진행하며 결과를 기록한다. 진행 중 기능 축소·권한 확대·새 서비스·비용 추가가 생기면 3.1로 올린다.

- **O-04** 체크리스트의 저장 구조, 본문과 폼의 연결 방식, Markdown 재가져오기 시 추가·교체 처리. 초안 §9, §21.
  - 근거: D-30은 같은 체크리스트를 어느 UI에서 다뤄도 동일 항목·상태를 참조하라고 요구한다.
  - 권장안: 체크 항목을 독립 엔티티로 두고 문서 본문의 체크리스트 블록은 그 ID를 참조한다. Markdown 재가져오기는 기본 "추가"로 하고, "교체"는 사용자가 명시적으로 선택한다.
  - 대안: 본문 블록을 정본으로 두고 폼은 본문을 파싱해 보여준다. 에디터 없는 화면에서 본문을 수정해야 하므로 권장하지 않는다.
- **O-08a** CRDT 저장 방식. 초안 §2, §8. OFF 모드 충돌 처리는 D-53으로 확정.
  - 근거: Tiptap 공동 편집은 Yjs 기반이며 Rust에는 호환 구현 yrs가 있다.
  - 권장안: 문서별 Yjs 업데이트 로그를 DB에 저장하고 주기적으로 스냅샷을 만든다. 리비전·diff·검색 색인·멘션 추출용으로 Yjs 상태를 JSON 투영하는 서버 측 레이어를 둔다(P-13).
  - 대안: 스냅샷만 저장하고 업데이트 로그를 버린다. 리비전 복원 요구(D-27)와 맞지 않아 권장하지 않는다.
- **O-09** RLS 세부 정책. 워크스페이스 간 공유·이동(D-24)과 사용자 소유 데이터를 어떻게 표현할지. 초안 §2, §19.
  - 근거: D-08은 RLS와 앱 권한 검사를 함께 설계하라고 한다. 워크스페이스 간 공유는 테넌트 단일 기준의 RLS로는 표현되지 않는다.
  - 권장안: 모든 행에 소유 워크스페이스 또는 소유 사용자를 기록하고, RLS는 "소유 테넌트 일치 또는 명시적 공유 테이블에 허용 행 존재"로 작성한다. 세부 객체 권한(문서별 비공개, 역할)은 앱 계층에서 검사한다. 앱 실행 역할과 마이그레이션 역할을 분리한다.
  - 대안: RLS를 생략하고 앱 계층만으로 검사. D-08에 어긋나므로 권장하지 않는다.
  - 진행(2026-10-17, 첫 흐름): 권장안대로 시작했다. 앱 역할(`fvoci_app`, NOBYPASSRLS)과 마이그레이션 역할 분리, 멤버십 기반 RLS(설정 없으면 거부), 정의자 함수·트리거로 번호·리비전·감사 불변식 강제. 워크스페이스 간 공유·이동과 개인 소유 데이터(개인 노트·시간 기록)의 RLS는 해당 기능에서 이어서 설계한다. 기록: `docs/development.md` 12절.
- **O-11** rhwp의 HWP 5.x·HWPX·구형 HWP 형식별 호환성 검증과 실패 시 대안. 초안 §2.
  - 권장안: 초기화 단계에서 표·수식·그림이 포함된 샘플 파일로 렌더링 품질을 확인하고 결과를 기록한다(D-42 방식).
  - 대안: 특정 형식이 실패하면 그 형식만 LibreOffice 변환 경유로 처리하거나 미지원으로 안내한다. 미지원 결정은 기능 축소이므로 사용자 결정으로 올린다.
- **O-19** `[해소: 구현, 권장안 채택]` 백그라운드 워커 구조와 배포 형태. 한 바이너리가 API와 작업을 모두 갖고 실행 역할(`FVOCI_ROLE=all|api|worker`, 기본 `all`)로 나눈다. 작업 기록(주기 작업 마지막 실행)은 PostgreSQL 테이블에 두며 새 서비스는 없다. 대안이었던 별도 작업 서비스·외부 큐는 운영 부담만 늘려 택하지 않았다. 작업 DB 계정 분리는 아직 하지 않았다(`docs/development.md` 27절).

  - 권장안: 단일 바이너리가 API와 워커를 모두 포함하고 실행 모드 플래그로 역할을 나눈다. 작업 큐는 PostgreSQL 테이블로 시작한다(새 서비스 추가 없음).
  - 대안: 별도 큐 서비스 도입. 새 서비스 추가이므로 필요해지면 사용자 결정으로 올린다.
- **O-25** Keycloak을 배포에 필수 포함할지 외부 OIDC 서버 연결만 지원할지. 배포 설계. 지침(인증 방식 전달 문구). `[해소: 구현, 권장안 채택]` `docs/development.md` 35절.
  - 근거: D-45는 Keycloak을 기준 제공자로 검증하되 표준 OIDC만 사용하라고 한다.
  - 권장안: 제품은 표준 OIDC 클라이언트로만 동작하고 어떤 OIDC 제공자든 설정으로 연결한다. 셀프호스트 기본 Compose에 Keycloak을 선택 가능한 프로필로 제공한다.
